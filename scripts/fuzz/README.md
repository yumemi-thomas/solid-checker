# Differential fuzzer

Finds checker violations that the real Solid 2.0.0-rc.21 runtime contradicts (false positives) and defects Solid reports where the checker is silent (false cleans), automatically. For each generated program it compares what the checker says at each site (violation, uncertifiable, none) with what the runtime says (dev diagnostics and thrown errors after driving the program). Only disagreements go to Chrome, the authority. It is operator tooling: its sweeps are not part of `make verify`, and the checker and the gates do not read it. Its own unit tests are (The tests, below).

## What a finding means

| verdict | meaning |
| --- | --- |
| `candidate-false-positive` | The checker proves a defect at a site. The runtime ran the site (the page shows its witness), with no diagnostic that claims the rule and no throw. Chrome decides. |
| `candidate-false-clean` | Solid reports a defect (a code the policy table calls a defect) where no checker finding covers it. Grouped by coarse key, confirmed in Chrome, shrunk: see False cleans. |
| `candidate-wrong-rule` | The runtime reports the defect at the finding under a code another rule of the same family claims: the checker named a real defect wrongly. |
| `known-open` | A false clean the ledger (`known-open.json`) accepts, by code and exact coarse key, with a cited reference. Not a failure. |
| `recall-gap` | Solid reports a defect and the checker declines (an uncertifiable finding at the diagnostic). Counted and ranked, never a failure. |
| `candidate-unexecuted` | Shown as `candidate-false-positive: unexecuted`. The checker proves a defect at a payload site the hit ledger shows never ran (see Unexecuted violations). A candidate, never a failure by itself: Chrome confirms it as `confirmed-unexecuted` (exit 3) or not. |
| `inconclusive` | The evidence cannot decide: the site never ran, nothing shows it ran, the rule has no runtime diagnostic, the program threw or halted reactivity, the checker or the runtime failed. Never counted as agreement. |
| `agree` | Both say the same at every site, or both are silent. |

A fast-path candidate is a hypothesis. A **confirmed** finding is a fast-path candidate that Chrome (`scripts/runtime-oracle.mjs`) also classifies `candidate-false-positive`. A candidate Chrome refutes is `refuted-by-chrome`: the fast path misled, which is a fast-path bug to note, not a checker bug. A candidate Chrome cannot decide (an `unattributed` diagnostic the oracle could not place on a line, a page error, a failed execution) is `chrome-inconclusive`: it is neither confirmed nor refuted, and a diagnostic Chrome could not place is never read as silence.

### Stop and report

When a run confirms a false positive (exit status 3), stop the sweep. Do not change the checker from inside a fuzzing session. Report the shrunk repro directory (`repros/<hash>/`, an oracle case: `App.tsx`, `oracle.json`), the rule and finding id, the signature, and the Chrome row. The owner decides whether it is a checker bug, a witness that does not prove what it should, or a runtime behaviour the rule should respect (invariants 1 and 2 of AGENTS.md).

## Profiles

`--profile <name>` picks what the generator draws. Without it a program takes one of the seven base profiles at random. The others are asked for by name and never drawn at random, so adding one does not move the seeds of any other: with no new flag, every profile prints the same programs for the same seed as before it existed.

| profile | what it generates |
| --- | --- |
| `closure-escape`, `default-param`, `helper-closure`, `in-place`, `async`, `mixed`, `body-call` | the base mix: a payload (a write or a read) in layers (closures, defaults, IIFE, `forEach`/`map`, helpers), a host scope, a disposition; legal decoys beside it |
| `owner-cleanup`, `owner-effect`, `owner-settled`, `owner-context`, `owner` | an owner-requiring call (`onCleanup`, `createEffect`, `onSettled`, `useContext`) in every host, owned or not (NO_OWNER_*, SETTLED_CLEANUP_UNOWNED, CLEANUP_IN_FORBIDDEN_SCOPE) |
| `disposal` | a write that runs while an owner is being disposed, behind a cleanup handle called now, later or never (see The disposal profile) |
| `misuse` | one program per claimed diagnostic code, the misuse at one marked site, in a chosen context, layer and binding (see The misuse profile) |
| `packages` | the helper layers are exports of a generated dependency package, `fz-lib` (see The packages profile) |
| `containers` | any base profile (mostly `disposal`) with statements wrapped in containers that run elsewhere, later or never (see Containers); `--containers` does the same on top of any profile |

## Install

The fast path runs in its own install, `scripts/fuzz/install`: the same pinned Solid packages and overrides as `scripts/runtime-oracle-install` (invariant 7, ADR 0453), plus `vitest`, `happy-dom` and `@solidjs/diagnostics`. A run refuses an install whose Solid packages are not 2.0.0-rc.17.

```sh
cd scripts/fuzz/install && npm install        # first time; commit the resulting package-lock.json
make runtime-oracle-install                   # the checker's, the type check's and Chrome's install
```

The type checker is `tsrs`, never `tsc` from node_modules. It is found from `--tsc <path>`, then `SOLID_CHECKER_TSRS_BIN` (`FUZZ_TSC` still works), then a release build in a `tsrs` checkout beside this repository, then beside the main working tree this worktree was made from. A run whose type checker is missing stops with exit 2 before it writes anything (every program would otherwise be a `type-error` and the run would pass with 0 candidates). So does a run in which more than half the programs fail to type-check, or all of them do (`TYPE_ERROR_REFUSAL_SHARE` in `typecheck.mjs`; a healthy sweep sees a few percent). Every entry point checks this: `run.mjs`, `matrix.mjs`, `equivalence.mjs`, `neutrality.mjs`, `disposal-check.mjs`, `packages-check.mjs`. The checker's findings are mapped to the program by realpath on both sides (the checker reports real paths; a work directory reached through a symlink, `/tmp` on macOS, otherwise dropped every finding and the run read as clean); a run in which the checker returned findings and none is under the program's directory stops with exit 2 (`assertFindingsMapped`).

**The browser.** Without `--browser`, the oracle and the Chrome host run the headless shell the pinned Playwright (`scripts/runtime-oracle-install`) names in its `browsers.json`, at that revision, in Playwright's cache for the platform (`scripts/playwright-browser.mjs`); a run stops when it is not installed (`cd scripts/runtime-oracle-install && npx playwright install chromium-headless-shell`). Before, they took the newest build in the cache, which another project's Playwright may have left: one cache held only Chrome 156 where Playwright 1.60.0 pins Chrome 148. The FLUSH_IN_EFFECT_CALLBACK recall grid (2,262 programs) gave every outcome and finding equal on both.

### The tests

`scripts/fuzz/*.test.mjs` (58 files, ~700 tests) are a lane of `make verify` (one `fuzz-tests` lane in its first step, beside the builds) and of CI's `scripts-and-cli` job. They were outside both (the `scripts/*.test.mjs` glob does not reach `scripts/fuzz/`), and a duplicate role-log arm id (`callee_roles.named-callback` tagged twice, which `roles.test.mjs` fails) reached main. `make fuzz-test [ARGS=<file>]` or `bun scripts/fuzz/test-lane.mjs --provision` runs them; `make verify-delta` selects the lane for any change under `scripts/fuzz/`.

- **Provisioned, not skipped.** Three tests need the pinned installs (`misuse-fire.test.mjs`, `api-fire.test.mjs`, and `cache.test.mjs`'s browser key), and `ssr.test.mjs`, `fast-daemon.test.mjs`, `checker.test.mjs` and three blocks of `codes.test.mjs` skip without them. `scripts/fuzz/provision.mjs` makes the machine ready the way the tsc oracle's `provision` does: idempotent (an install that passes the pin check is left alone, so a provisioned Mac spends milliseconds), `npm ci` from the lockfiles for `scripts/fuzz/install` and `scripts/runtime-oracle-install`, and `npx playwright install chromium-headless-shell` for the pinned shell. It needs `npm` and the network only when something is missing. `--check` verifies only and fails naming the command. This was chosen over a lane that fails when unprovisioned because verify must work on a fresh CI runner and on the owner's Mac without a manual step; a failed provision still fails the run in its first seconds, never as a skipped test.
- **No silent skip.** `scripts/fuzz/test-lane.mjs` runs vitest under Node (the fuzzer is Node tooling; `ssr.mjs` needs `node:module`'s `stripTypeScriptTypes`, which Bun lacks) with a JSON report, and fails the lane on any skipped test. The one exception is the three files that need a `tsrs` binary (`checker.test.mjs`, `rewrite.test.mjs`, `tsc-overlap.test.mjs`; tsrs is a separate repository and not provisionable here): with no tsrs found they may skip, and the output names them (`not run, no tsrs binary`); with tsrs found they must run. CI has no tsrs, so those tests run on a machine that has it (`make verify` on the owner's Mac).
- **Cost.** ~2.7 minutes on the Mac (702 tests; `rediscovery.test.mjs` is ~2.5 of them), beside the builds, ~3.5 minutes there, off the critical path of a full `make verify` (the first step takes ~7, bound by the WASM package build; beside the gates it was the longest lane, +~2 minutes).

### The Linux VM

On a Mac whose endpoint-security agents gate every process start, the checker's and the producer's starts bound the whole run: one such Mac started at most ~127 processes a second (`/usr/bin/true`), checked ~12 fuzz programs a second at any concurrency, and ~3.5x more with the binaries copied to `/private/tmp` (the agents check binaries under the home directory longer). In a Linux VM a start is free. `scripts/fuzz/vm.sh setup` makes one (Colima on Apple's Virtualization framework, a vCPU per performance core, the repository's toolchain pins, a clone of this checkout on the VM's own disk, the pinned Chrome); `scripts/fuzz/vm.sh run <command>` syncs the clone to this checkout as it is (HEAD, its changes and its new files; not ignored ones), rebuilds what moved and runs the command there; `detach <log> <command>` does the same detached from the SSH session (a full-grid run outlives a host time limit, a dropped session and a sleeping host; its output goes to `<log>` in the VM); `pull` copies a run out. Grid outputs and caches live on the VM's data disk: when the workspace is on the small root disk (Colima mounts a non-default profile's data disk at `/mnt/lima-colima-<profile>`), setup moves `runs/` and `tmp/` there, and every sync refuses to start with under 10 GiB or 10% of the inodes free (a program is a directory of files: three full runs filled 9.8 million inodes, and the run failed late with ENOSPC, harness rows and a hung Chrome). On that Mac the FLUSH_IN_EFFECT_CALLBACK recall grid took 250 s with the binaries in the home directory, 70 s from `/private/tmp`, 19 s in the VM (warm; 49 s on its first run), every outcome and finding equal. A vCPU runs a tight loop 25% slower than a native performance core; 12 vCPUs held that against 12 native threads.

What a run writes in the VM stays in RAM unless it is a result. The VM's disks are image files in the host's home directory, so every write in the VM is a write the host's file-system services follow. `vm.sh` mounts tmpfs over the per-program work directories (the checker's, the fast runtime's, Chrome's) and over `$root/ram`, which holds TMPDIR (a producer's transition arena per process, Chrome profiles) and the focus runs' scratch (`SOLID_CHECKER_FUZZ_SCRATCH`, `focus.mjs --scratch`): each grid's `cases/` and `chrome-cases/` live there behind links at their usual paths (scratch.mjs), until `--prune-cases` deletes them. Results (programs.jsonl, matrix.json, roles.json, the logs, the raw role log) and the runtime cache stay on the data disk. On mx-recall NO_OWNER_CONTEXT (18,655 programs, `--split-codes --prune-cases --role-log`, 2026-11-02) a run wrote 1.1-1.8 GiB to the VM's disks before and 34-53 MiB after, with every outcome equal to full-8's. A recall code's cases take up to ~3 GiB of tmpfs pages; the ceilings are `FUZZ_VM_SCRATCH_GIB` (8, each work directory) and `FUZZ_VM_RAM_GIB` (16).

**The role log is not in the scratch.** It is one file the grid's checkers append to, and it is large: the role logs of a full non-lean lg-recall reached 7.5 GB, filled the 16 GB tmpfs beside the cases and Chrome's profiles, and the kernel OOM-killed a 103k-program `legal.mjs` while later units failed with ENOSPC writing `cases/oracle.json`, judged as thousands of `harness` rows (2026-11-03). `focus.mjs --role-log` writes `<grid>.roles.jsonl` beside the grid output, on the data disk, with or without `--scratch`; being one appended file it costs the host's file-system services a stream of writes to one file, not an event per program, and `--prune-cases` still deletes it once folded. Before every unit `focus.mjs` checks the free space of the grid output (where the role log goes) and of the scratch (`roomAt`: under 5 GiB, `SOLID_CHECKER_FUZZ_MIN_FREE_GIB`, or 5% of the inodes free), measuring a directory not created yet at its nearest existing ancestor. A place without room stops the run before the unit starts, exit 2, with `needs a look: stopped: <unit>: not started, scratch (<path>): 1.5 GiB free`; a unit whose log or flagged rows show `ENOSPC` says the disk filled (those `harness` rows are that, not the checker) and stops the run, since the next unit would fail the same way.

The disk images themselves can leave the home directory: `FUZZ_VM_PROFILE=sc scripts/fuzz/vm.sh relocate-disks ColimaVM` creates the APFS volume `/Volumes/ColimaVM` in the Data volume's container when it is missing (`diskutil apfs addVolume`, which erases and resizes nothing), turns off its FSEvents log (`.fseventsd/no_log`: the volume's owner moves the root-owned `.fseventsd` aside, writes its own, and remounts), Spotlight (`.metadata_never_index`) and Time Machine for the image directories, stops the VM, copies the root and data images there (`dd conv=sparse`, then `cmp` against the originals), renames the originals `*.pre-relocate`, links the instance's paths to the copies and starts the VM, checking that Virtualization.framework's VM process holds the copies open. `relocate-disks --remove-old` deletes the originals once the VM is running from the volume. `setup` warns while an image is still a plain file in the home directory. The 150 GB data image copied in a few minutes with `dd` at 64 MiB blocks; macOS `cp` managed 20-50 MB/s on a loaded host.

Per-program startup: one check of a cheap mx-recall NO_OWNER_CONTEXT program takes ~27 ms run by itself in the VM, ~13 ms of it in `sidecarSpawnNs` (starting the producer and opening its program; a process start alone is ~0.5 ms). `--warm-checker` (ADR 0543; `run.mjs`, `matrix.mjs`, `legal.mjs`, `focus.mjs`; the Rust executor's default) recovers that share: a slot's feedback-facts check goes to a retained checker daemon, one per slot directory (a warm slot keeps one directory, `slots/<n>/program/`, since the daemon is keyed by the project path; ADR 0545), which resyncs the slot's rewritten files as overlay updates (the type check's `tsconfig.tsbuildinfo`, created and removed between checks, no longer rebuilds it). A step-1 worker takes the queued program whose file names and tsconfig.json a free slot last held (ADR 0592; at most four times the workers' requests pass an older one), so the daemon updates its program instead of reopening it: a third of a grid's programs change the file set, and a reopen costs about twice an update. The checker it starts runs its own fan-outs on one worker (ADR 0594: `SOLID_CHECKER_IR_WORKERS`, `SOLID_TYPEFACTS_PER_FILE_WORKERS`, `RAYON_NUM_THREADS` at 1 unless set): the executor already runs a check per core. A killed or failed warm check stops its daemon (`--stop-daemon`, which waits for what it accepted, at most 60 s) before the slot goes to the next program, and the executor stops every slot's daemon at its end. With the role log each check names its program (`SOLID_CHECKER_IR_ROLE_LOG_PROGRAM`, the path lines' `g`, which `roles.mjs` takes over the path), and the daemon logs each answer to the log and program its client names (ADR 0545). `--warm-verify` also runs the one-shot check at the same path after each warm one: a difference in stdout or exit status makes the program a harness failure. `node scripts/fuzz/warm-identity.mjs --code <code> --count N --concurrency C --out <fresh>` runs step 1 of generated programs (both type checks and the checker, no Chrome) in passes off, on and verify, and fails on any difference; `--role-log` also folds the off and on passes' role logs and fails unless they are equal, and `--churn` orders the programs (several codes interleaved with `--code A,B`) so that consecutive ones' import lines differ. On the Mac at concurrency 7: NO_OWNER_CLEANUP (3,000 programs) 128-132 → 168-169 programs/s, mean check 44 → 30 ms; STRICT_READ_UNTRACKED (2,000) 132 → 194 programs/s, 44 → 20 ms; every warm answer byte-identical to the one-shot answer at its path. A daemon closes the descriptors it inherited and the executor starts one process at a time (an inherited pipe once held a grid's `prepare` open). Alone, a warm check is ~12 ms when the program's import lines are the slot's previous program's and ~25 ms when they differ (the producer's update then re-resolves), against ~30 ms one-shot. It is the Rust executor's default since warm-verify-1 (2026-11-02): mx-recall NO_OWNER_CONTEXT, lg-recall NO_OWNER_CLEANUP and a 10% sample of mx-recall REACTIVE_WRITE_IN_OWNED_SCOPE under `--warm-verify`, 48,973 programs with Chrome, every warm answer byte-identical to the one-shot one; `--no-warm-checker` turns it off.

## The boundary registry (ADR 0935)

A clean is only as sound as the premise of the item that gave it. The proof log (ADR 0933) fails a clean nothing explains; it cannot fail a *wrong* proof, an arm that answers silent through a premise that is false for some legal program (the four arms of ADR 0927, the `<For>` row handler of ADR 0932: each was reachable by legal programs, and no grid held one where the premise failed). `boundary.mjs` holds, per item that can make a site silent, the premise and a **pair**: a misuse program and a legal one that differ only in the fact the premise claims.

| item | where it comes from | evidence |
| --- | --- | --- |
| tagged arm (`role_arm!`) that can answer a silent role: 121 | `boundary-inventory.mjs` reads the Rust source | a measured witness (below) or a stated gap |
| named end (`proof_log::end_at/end_with`): 36; `PremiseKind`: 37; `DropPass` through its kinds | same | a premise: a pair, a fixture directory, or an `outside` reason |
| row of the checker's own tables (`timing_behavior`, the schedulers, carriers, dispatch lists): ~300 | same | the table family `tbl-*`, a dispatch pair, or a stated gap |
| dialect question (`impl Dialect for Solid2`): 133 | same | vocabulary, source or role, with the primitive contexts as family evidence |

Not required, each stated in `boundary.test.mjs`: `Unknown` arms (an obligation), reporting arms (a wrong answer is a false positive, which the grids' judge finds), owner arms (ADR 0886's `ARM_ENDINGS`).

- **Pairs** (`boundary.mjs`): context pairs on the generator's own contexts (`kept-*`, `apply-void-*`, `owned-updater-*`, `evt-row-*`, `site-reach`, `fire-*`, ...), layer pairs (a hand-off, depth, chain, control or file layer around the same site in a window and out of it), callback-form and mount pairs, the table family's pairs and the boundary wrappers'. Each code splits a pair's contexts by its own lists (`SPEC`).
- **The table family** (`table-shapes.mjs`, contexts `tbl-<row>-<variant>`, recall grids only, the plain shape of each variant): one row of `argument_behavior` / the schedulers / the carriers each. `real` is the exact API, run where its class allows (inline rows in a window or a handler; host-run rows legal; listeners, thenables, bound functions and collections with the synchronous path that runs the function in the window); `shadow` declares the same spelling with the opposite behaviour (a local `setTimeout` that calls its callback; a local `map` that only keeps it): invariant 3, a name-only match is wrong either way. The variant names where the function is handed over (`b` body, `u` closed `untrack`, an allowed region) and where it runs (`h` handler). Rows no program can run are in `TABLE_GAPS` with the reason (`findLast` is TS2550 under the fuzz tsconfig's ES2022 lib, `new Set(f)` throws, ...).
- **The arm-coverage shapes** (`arm-shapes.mjs`, `barm-*`): contexts for tagged arms no fixture program reached (`bun scripts/proof-ablation.mjs` lists them as unwitnessed), each beside the twin that differs only in the arm's fact: a generator stepped by a spread in the body, in a click handler, or by nothing; a sync generator drained by an async function that awaits between the steps or not; a read in a layer of a `<For>` row's body before or after an await. Recall contexts, base shapes.
- **`node scripts/fuzz/boundary-scan.mjs`** runs cells through the checker alone (no Chrome) with the role log on: the verdict at the site and in the program, and the arms that answered. A screen, seconds long: a misuse program with no finding anywhere, a legal program with a violation, are candidates Chrome (`focus.mjs`) decides.
- **`node scripts/fuzz/boundary.mjs verify [--ablate] [--update]`** runs every pair's programs and writes `boundary-witnesses.json`: per pair and code what each side came to, per arm the clean legal cells it answered silent in (`decisive` when `SOLID_CHECKER_IR_ABLATE_ARM=<arm>` makes a finding appear there: the proof-log branch's build). An arm is *separated* when it has a witness in a pair whose misuse side, for that code, left no program clean. Commit the snapshot with the change that moved it, as coverage snapshots are.
- **`boundary.test.mjs`** (a lane of `make verify`) fails when an item has no pair, fixture or stated gap, when a gap is stale (`boundary-gaps.mjs` only shrinks), and when the snapshot names a pair, code or context the registry or generator does not have.
- **`bun scripts/proof-ablation.mjs`** counts, per arm, the sites that stand on it alone (clean to obligation), the sites where two arms disagree (clean to violation: a soundness signal, every one listed), violations that become obligations, and the rest, over the fixture projects (`--logs <proof-gate --out dir>`) or a grid (`--grid <dir>` with its `cases/` and `<dir>.roles.jsonl`).

## Running

The short loop, after a change to a shape or a rule: `make fuzz-focus CODES=A[,B]` runs the six grids (misuse and legal; base,
sources, combinations) restricted to those codes, on the Rust executor (`--executor rust`) and the Chrome host, each with an
oracle sample stratified by code, context and outcome, and exits 1 when something needs a look (a false clean, a wrong rule, a
false positive, a contradicted legal program, a harness failure, a behaviour difference from the oracle). About 1.5 minutes cold
for one code, under a minute when the cache holds its programs. The full grids, with the full oracle sample, run before a PR:
`node scripts/fuzz/focus.mjs --codes all --grids mx-base,mx-src,mx-combo,lg-base,lg-src,lg-combo,mx-recall,lg-recall --split-codes --prune-cases`
(`--split-codes`: one grid process per code, so mx-recall's 277k programs stay within a heap and a hang costs one code;
`--prune-cases`: each grid's `cases/` deleted once its rows are read; `--grid-timeout <minutes>`, default 120, kills and reports a
grid process that hangs; `--heap-mb`, default 12000 for the recall grids; each grid's output streams to `<grid>.log` as it runs).
A grid process that stops before writing `programs.jsonl` (a killed executor, a refusal, an uncaught error: `matrix: stopped: …`,
`legal: stopped: …`) is a harness failure that needs a look, never `0 programs {}`: the unit prints `STOPPED, N programs judged
before`, gives the reason from its log, and keeps the rows judged so far (`programs.partial.jsonl`, appended per chunk; partial.mjs).
The executor drains the Vite helper's stdout after its ready line and the helper ignores `EPIPE` (a pipe closed after that line killed
the helper 112,050 programs into an mx-recall grid, 2026-11-03); a helper or browser that exits is still restarted, its in-flight
programs `harness` rows (main.rs `MAX_RESTARTS`).

**Sampling the big codes while iterating.** STORE_WRITE_OUTSIDE_SETTER and REACTIVE_WRITE_IN_OWNED_SCOPE are about 40% of a full
run. `focus.mjs --sample-big <fraction>` passes `--grid-sample` to every grid (`matrix.mjs`, `legal.mjs`; sample.mjs): each (code,
context, layer, variant) stratum of those codes keeps that fraction of its programs, at least `--sample-big-min` (1), the ones whose
`fnv(<seed>:<id>)` is smallest (`--sample-big-seed`, default 1), so the pick is reproducible and does not depend on the grid's order;
`--sample-codes A,B` names other codes; every other code stays whole. Each sampled grid records `gridSample` (settings, kept of how
many, strata) in matrix.json or legal.json, the focus summary prints it and ends with `sampled (...), not a full run`, and the matrix
gate refuses a sampled matrix on either side. A run without the flag is complete: the full run before a PR (above) never takes it.
Measured on the VM (2026-11-02, `--sample-big 0.1 --runtime-diff 0`, runtime cache cold): STORE_WRITE_OUTSIDE_SETTER's mx-recall kept 33,216 of 254,112 programs (15,438 strata, so the floor of one each lifts 10% to 13%) in 393 s; REACTIVE_WRITE_IN_OWNED_SCOPE's mx-recall 12,756 of 110,712 (4,068 strata) in 162 s and its lg-recall 9,240 of 79,746 (3,060 strata) in 142 s. On lg-recall FLUSH_IN_EFFECT_CALLBACK (`--sample-codes`), a sampled run's 672 rows each equal the full run's, two sampled runs pick the same 672, and the run without the flag keeps all 5,034, equal to the run before the option existed.

**Splitting a run across machines.** `focus.mjs --shard i/N` passes `--grid-shard i/N` to every grid (shard.mjs): each
grid keeps the programs whose `fnv("shard:<id>") mod N` is i, so the N shards partition the run (every program in exactly one, the
pick fixed by the program ids alone), and the N shard runs together are the full run, unlike a sample. Each shard grid records
`gridShard` (i, N, kept of how many) in matrix.json or legal.json and the focus header says so; the matrix gate compares a shard only
with the same i/N of the baseline, and perf-compare treats a different shard as not comparable. Each shard takes its own oracle sample
over its own programs, so N shards compare more programs in Chrome than one whole run. With `--split-codes`, a GitHub-hosted runner
(4 vCPU) judges about 8 programs a second, so a code of 250k programs needs about 20 shards to stay inside a 6-hour job.

A grid writes `selected` (the programs it kept after `--ids`, the sample and the shard) in its report. A unit that judged no program
is flagged unless its process finished and `selected` is 0: a code with no shape on the grid's axes (no source shape on mx-src, say)
or a shard that got none is printed as `no programs`, not as a problem; with `--split-codes` a code that no grid of the run judged a
program of still needs a look, and so does a run that judged none.

**The audit on CI.** `.github/workflows/fuzz-audit.yml` runs the full run nightly (01:00 JST, recall grids lean) and weekly with every
recall value (`--recall-full`; Sunday 16:00 UTC, Monday 01:00 JST), and on demand (Actions, Run workflow, any branch; the `recall` input
chooses lean or full) on free GitHub-hosted runners, through `audit.mjs`: 40 shards (`--shard i/40`, every code and grid, no oracle; each grid writes
`oracle-candidates.jsonl`, the programs its runtime differential would take), then `audit.mjs pick` builds each grid's oracle sample
from every shard's candidates (per stratum the smallest `fnv(id)` with a fast record, as `sampleStrata` picks over a whole grid, so
the sample is a local full run's), one runner per grid and part runs the differential on it (`--ids`, picked by id before generation;
`oracleParts` gives every grid one job, then one more part at a time to the grid whose part is largest, up to `ORACLE_RUNNERS` (20, the
account's concurrent runners: GitHub starts a matrix in no fixed order, so a queued job may be any part) while that part is over
`ORACLE_PART_FLOOR` (200) programs; every N-th id; ADR 0620), and
`audit.mjs report` judges the run: every shard present and whole, PROBLEMS rows, oracle behaviour differences and inconclusive or

The report fails the workflow when something needs a look and is the run's step summary. Each shard carries its warm state to the
next run (the runtime and type-check caches, and the installs and browser their keys hash by mtime, in a pax tar); measured on one

Rediscovery (AGENTS.md): a defect found any way is closed when the grids generate its shape and the build that had it fails `make

## False cleans (phase D)

A **false clean** is a runtime diagnostic of a defect code with no checker finding that covers it. Which codes are defects is the policy table in `codes.mjs`: every rc.17 dev code has `{ rules, disposition, severity }`, and `codes.test.mjs` greps `code: "X"` across the pinned dev dists of the fast install and fails on a code the table does not classify (so a Solid bump cannot add noise silently) or a severity that differs from the dist. Dispositions: `defect-claimed` (a rule claims it), `defect-unclaimed` (a recall gap by "never quieter than Solid"), `consequence` (the engine's reaction to an earlier failure), `advisory` (Solid documents it as legal; a rule may still report it as an optional warning, but silence is no miss: `ASYNC_OUTSIDE_LOADING_BOUNDARY`, a boundary-less async mount, SPEC-ASYNC-SEMANTICS A6, reported by SC5003 as a warning), `out-of-scope` (SSR, host attribute checks, codes the published typings already reject).

Per runtime diagnostic of a defect code: a checker violation there is `agree`; an uncertifiable finding of a rule that claims the code, of a withholding rule, or of a rule that declines it (`declining` in `codes.mjs`: SC4001's obligation on a `useContext` read declines CONTEXT_NOT_FOUND, while its violation there stays `wrong-rule`) is a `recall-gap`; nothing that could claim it is a `candidate-false-clean`. "There" is any line of the diagnostic's stack, and the line of the call that registered a callback the stack runs through: a callback handed to `onSettled(cb1)` runs later, so its stack holds the lines inside `cb1` and never the registering line, where the checker answers (`registration.mjs` reads the link from the program tree: a stack line inside `const N = ...` belongs to the primitives that take exactly `N` as their callback, `N` declared once). A frame in another module of the program (`el.ts`, `helpers.ts`) is mapped through that module's own transform, and the matrix judge reads that module's findings (`moduleFindings`) at its frames only, by the same position rules (ADR 0921); the other judges read App.tsx's. The dev compiler maps a compiled `insert`, `effect` or `memo` to its element, attribute or fragment: the host records, on such a top frame, the start of the value the call was handed (`compiled`, only where the map has a segment there, `served.mjs`), which places a claiming or declining finding, never a withholding. A diagnostic no line could be given for is a false clean only when the checker has no claiming finding anywhere in the file. `ASYNC_OUTSIDE_LOADING_BOUNDARY` is reported by the scheduler, so it never has an authored line (`placelessCodes` in `codes.mjs`): `run.mjs` judges it by file, as the matrix does. A claiming violation anywhere in the file agrees with it, only declining claiming findings make it a `recall-gap`, and no claiming finding makes it a false clean.

The pipeline (`falseclean.mjs`, `falseclean-run.mjs`):

1. **Coarse key** = the code, the chain of primitives above the owner call (`root>untrack`, `memo`), and the dynamic stack shape (the roles of the diagnostic's frames: a primitive, a handler, JSX; wrapper functions and calls are left out). Closure layers, helpers and decoys do not change it; the fine signature (`dedupe.mjs`) keeps them apart. The frames are read through `print.mjs`'s `lineTable` (line to node path), not the nearest site by line. On the 179 Chrome-confirmed owner diagnostics of phase C the key gives 55 groups (15 to 18 per code).
2. **Ledger** `known-open.json`: `{ code, coarseKey, ref, reason }`, one exact key each, no wildcards. `ref` is `open-work.md#<anchor>` of a heading that exists, or `ADR nnnn` of a decision that exists; a bad ledger stops the run before it starts. A false clean matching an entry is `known-open`. A run reports the entries that did not fire (`stale-open` when the run covered the profile the entry came from). `--ledger <path>` or `--no-ledger`.
3. **Confirm**: with `--confirm-with-chrome`, one representative per new group (the smallest program) is run in Chrome. Confirmed means Chrome reports the same code at the same innermost App line with no covering finding. A diagnostic Chrome reports but could not place counts too (`confirmed-unplaced`): for a false clean, Solid spoke. Other outcomes: `line-differs`, `covered-in-chrome`, `refuted-by-chrome`, `chrome-inconclusive`.
4. **Shrink** (`--shrink`): the predicate is the same code, the same coarse key and no covering finding; the control is the legal twin, the program with its payload replaced by a literal, which must report no diagnostic of the code. The minimum is run in Chrome again and its status is reported (`minimum confirmed`); the fast path alone can drift.
5. **Exit status 4**: a confirmed false clean with a coarse key the ledger does not know. The sweep still runs to the end (exit 3, a confirmed false positive, stays the stop).

`findings.json` has a `falseClean` section (groups worst severity first, `knownOpen`, `staleOpen`, ranked `recallGaps`); `summary.json` carries the counts.

## The misuse profile and the recall matrix

The fuzzer above hunts a checker that is too loud (false positives) or silent where Solid speaks (false cleans) in programs it draws at random. The **misuse profile** (`--profile misuse`, `misuse.mjs`) asks the other question on purpose: for every code a rule claims (the `defect-claimed` rows of the policy table), does the checker report a violation when the primitive is misused? Each program targets one code at one marked site (a `use` node), so a matrix cell is unambiguous.

* **Context** (the matrix column): component body, memo, effect compute or apply, render-effect compute or apply, `createTrackedEffect`, `onSettled`, `untrack`, `createRoot`, `runWithOwner(null)`, event handler, timer, promise callback, microtask, after an `await`, a JSX child (plain, under `Show`, in a `For` row), an `action` body, an async memo or effect compute. A code's list (`SPEC[code].contexts`) holds only the contexts where the call is a defect and the runtime reports it; `misuse-fire.test.mjs` fires every cell in the fast runtime.
* **Layer** (random per program): none, a named closure called in place, a same-file helper taking the callback, an IIFE, or two of them.
* **Binding** (random per program): the API reached by a direct import, `import * as S`, an alias (`flush as flushAlias`), a destructuring (`const { flush } = S`), or a wrapper function (the wrapper's inner call line belongs to the site, `aux` in `sites.json`).
* **typed-away**: a code whose every misuse the published typings reject has no template (`ASYNC_STORE_SETTER`: an async setter callback is TS2345). It is recorded with the type checker's error, never counted as a gap (invariant 1). `MISSING_EFFECT_FN` has a recall-only template now: rc.17 reports it when the apply is `undefined` (`@solidjs/signals` dist/dev.js:2504-2518), which type-checks behind a cast (`undefined as unknown as () => void`, `undefined as any`); its one-argument and one-tuple spread calls are typed away on purpose (below).

`matrix.mjs` runs `--per-cell N` programs per (code, context) and judges each at its site:

| column | meaning |
| --- | --- |
| typed-away | tsc rejects the program; not evidence of recall |
| tsc-overlap | tsc rejects the program and a checker violation covers the rejected code (`tsc-overlap.mjs`): a candidate breach of invariant 1, never dropped |
| harness | the checker or runtime run failed; not evidence |
| not-fired | the program type-checks and the runtime did not report the code at the site; a violation there that ran is a `false-positive`, and a second code is judged as on any row (ADR 0615) |
| agree | runtime-confirmed, and a violation of a rule that claims the code covers the site |
| wrong-rule | runtime-confirmed, and only another rule's violation covers the site |
| recall-gap | runtime-confirmed, and only an uncertifiable finding covers the site |
| false-clean | runtime-confirmed, and no finding covers the site |
| false-positive | an `agree` or `recall-gap` program with a violation off the site (a decoy's, a parent's, a helper call's line) whose lines ran in an undisturbed run that reported no code of its rule anywhere (classify.mjs `offSiteVerdicts`; `detail.primary` keeps the site's outcome) |

Only runtime-confirmed programs (agree + wrong-rule + recall-gap + false-clean + false-positive) count in the checker columns. Off-site violations are judged in both grids (the legal grid turns `clean`, `uncertifiable` or `unexecuted` into `false-positive` the same way); one whose rule's code the runtime reported elsewhere is `unconnected` (`detail.offSite`, `matrix.json` `offSite`), counted and never failed, since the frames may not show the call the finding means. A recall gap names the mechanism that declined (`detail.declinedBy`: the claiming rule, a withholding SC9012, or a declining rule; `recallGapBy`). A second code on the site's lines that the checker misses in a file with no uncertifiable finding is `secondary: false-clean-certified`, which `focus.mjs`, the audit and smoke flag as `secondary-false-clean` (`codes.mjs` `rowProblem`, their one test) and the gate fails when a cell gains one. The gate fails a program entering `false-positive`, and one entering `not-fired` from a false clean or a recall gap (the miss would leave the measure). A legal program whose run was disturbed before its site ran is `disturbed`, not `clean`. The matrix measures the `defect-claimed` codes only: an advisory code has no cells, and a baseline cell of a code that has become advisory is reported as `retired` by the gate, never as a regression (`ASYNC_OUTSIDE_LOADING_BOUNDARY`'s three cells, 60 programs).

**Typed-away programs and tsc overlap.** The grids (`matrix.mjs`, `legal.mjs`) run the checker on a program `tsrs` rejects too, and never its runtime (`checkTypedAway` after each chunk's evaluation; the Rust executor stops at a failed type check, so the checker runs in a second call, as for a type-check spot check; outside pipeline.mjs, so no runtime-cache key moves). A violation of any rule whose line range holds a line tsrs rejected in App.tsx, or a violation of a rule claiming the cell's code anywhere when the rejected line is the site's own, makes the program `tsc-overlap` in either grid (`typedAwayVerdict`): invariant 1 says the checker stays silent on what tsc reports, so the pair (the TS error, the violation) is surfaced, in `focus.mjs` PROBLEMS, the smoke ranks and the gate (entering it fails, from a typed-away baseline too). It is a candidate, not a verdict: "a different claim about the same code (ownership, timing) is allowed", so the owner either deletes the rule's case (recorded in fixtures/tsc-oracle) or records the pair in `ACCEPTED` with its reason. A violation elsewhere in a typed-away file is listed (`detail.elsewhere`) and not judged. The finished grids of the 644bd1a81 run held no typed-away program, so the change costs a checker run per typed-away program and nothing else; the typed-away templates below are what it judges.



```sh
node scripts/fuzz/matrix.mjs --out <fresh dir> --seed 1 --per-cell 20 --confirm-with-chrome --shrink --checker-label <commit>
node scripts/fuzz/matrix.mjs ... --baseline <saved matrix.json>         # gate: exit 1 on a regression
node scripts/fuzz/matrix.mjs --gate <baseline.json> <current.json>      # compare two recorded matrices
```

**Grid.** `--grid` replaces the `--per-cell` random draws with one program per shape of every cell: each variant, binding and layer the template has (`gridShapes`), 3580 programs in all. A shape's seed depends on the run seed and the shape only (`shapeSeed`), so adding a variant or a context moves no other shape's program. On the recorded matrices every program of one shape had one outcome, and no smaller key did; the 2100 random programs covered 1395 shapes of the grid, and each program that moved between two recorded matrices moved with its whole shape. So the grid judges what the random draw judges, and reaches the shapes the draw misses. A grid matrix records `sampling: "grid"`; the gate refuses to compare it with a random one, so it needs its own baseline.

**Value bindings (grid only).** A component-scope value (a setter, an accessor, an action, a store) also comes through a hook that returns it in an object (`hook`: `const { useIt } = useThing()`), that hook's result used through a member (`hook-member`: `thing.useIt()`), and a tuple slot (`tuple`: `const [, useIt] = pair`), the shapes real code hands a value on in (`VALUE_BINDINGS`, `gridBindingsOf`). They are never drawn at random, so the random matrix keeps its programs and its baseline. The `destructured` binding of a value is an object literal (`const { useIt } = { useIt: r1 }`), which real code rarely writes; of an API it is the namespace form (`const { flush: flushD } = S`), which it does.

**Certified false cleans.** A false clean in a file the checker has no uncertifiable finding in at all is `certified` (`detail.certified`, `falseCleanCertified` per cell and in total, the item's `certified` in `run.mjs`, `certifiedFalseCleans` in its summary): the checker claims it proved the whole file, so the miss is a fail-closed break (invariant 2), not a recall gap that lost its place. `matrix.md` also tables the outcomes by binding x layer across codes (`byFeature`), so one root cause counts once.

**Unclaimed defects.** The matrix measures the `defect-unclaimed` codes that have a template too ("never quieter than Solid"): `PRIMITIVE_IN_EFFECT_CALLBACK` (a memo, effect or root created with no owner in an effect's apply). `ASYNC_STORE_SETTER` is typed away: the setter callback is `(state) => void | T`, so an async callback is TS2345 and tsc already reports it. The others have no template: `UNCOMMITTED_INPUT_OVERWRITTEN` needs a real value edit (the drivers dispatch synthetic events), `RUN_WITH_DISPOSED_OWNER` is decided not to build, `LOADING_ON_OUTSIDE_HOLD` is niche. `PENDING_ASYNC_FORBIDDEN_SCOPE` (a pending read in `onSettled` or `createTrackedEffect`) is claimed by SC5001 and has its template.

The gate compares the baseline's programs: a program only the current run has (a grid shape added since) is reported as new, never as a regression.

**Runtime cache.** Solid's answer on a program does not depend on the checker. `matrix.mjs`, `legal.mjs` and `run.mjs` keep each program's fast-path record under `--cache-dir` (default `$TMPDIR/solid-checker-fuzz-cache.noindex`, beside the neutrality baseline), keyed by the case's files as a runner reads them (`executionFiles`: no `program.json`, `sites.json` as its plan and sites, the oracle files without their `note`) and by an environment key: the sources that produce a record (`RECORD_SOURCES`: the fast path and its runner tree, the type check, `checker.mjs`, Chrome and its hit parsing, the pipeline, `cache.mjs`), `scripts/runtime-oracle.mjs` without its `codeRules` claim table (the type check compiles its entry; the table only judges a record, and editing it to claim a code once re-ran every record: `oracleRecordHash`), the clock, the `tsrs` binary and both installs' lockfiles. The checker is not in the key, so a run after a checker fix reruns only the checker. **Type checks** have a cache of their own beside it (`typecheck-<key>/`), keyed by the bytes of the project the type check compiles (`checkerProjectFiles`: App.tsx or the twin, the modules, `main.tsx`, `tsconfig.json`, packages; `typecheckKey`) and by `typecheckEnvironmentKey`: the `tsrs` binary, the rc.17 install's lockfile and what it holds (`treeStat` of its node_modules) and the harness that runs and parses `tsrs` (`TYPECHECK_SOURCES`: `typecheck.mjs` and the executor's `exec/src/typecheck.rs`). It does not depend on the checker, the runtime, the fast or Chrome host, the clock or the oracle, so it holds when the runtime key moves; before, the type checks were runtime-cache entries and an edit to the pipeline, the Chrome host or the executor re-ran every one. On the VM's lg-recall FLUSH_IN_EFFECT_CALLBACK grid (5,034 programs, 10,068 type checks) the evaluation took 53 s with both caches cold, 39 s with the runtime key moved and the type checks cached, 25 s with both warm; every row equal to an uncached run's. It stays on with `--real-clock`; `--no-cache` turns it off. A record the machine produced (a runner that wrote nothing, a type check killed by its timeout) is never stored. `matrix.json` does not change; the hits and misses go to `cache.json` beside it. `--no-cache` turns it off, and so does `--real-clock`, whose records depend on the machine. `run.mjs` writes its `cache.json` the same way, and its `results.jsonl` differs from an uncached run's only in `runtimeMs` (a cached record keeps the wall time it was recorded with; `compare-runs.mjs` ignores timings).

**Staleness.** Every cache (the neutrality baseline, the runtime cache, the Chrome cache) keys on what its entries depend on, and the two new ones check themselves:

| cache | key | check |
| --- | --- | --- |
| neutrality baseline | the generator version, the judging sources, `runtime-oracle.mjs` (the checker reads its entry), the checker and type-facts binaries, `tsrs`, the clock, both lockfiles, `installedKey`; per row the program's seed and the hash of its case files (`--containers` and the misuse pins draw other programs from the same seed) | none: it holds checker verdicts, so the checker binary is in its key |
| runtime | the case files; the record sources, `runtime-oracle.mjs` without its claim table, the fast host, the clock, `tsrs`, both lockfiles, `installedKey` | the first 3 fast-record hits of a process run fresh as well (`SPOT_CHECKS`); a difference (`recordDigest`: every diagnostic with its positions, throws, witnesses, hits, order, quiescence, failure phase) stops the run with `StaleCacheError` |
| type check | the project's bytes; `tsrs`, the rc.17 install's lockfile and `treeStat`, `typecheck.mjs` and `exec/src/typecheck.rs` | the first 3 hits of a process run fresh as well; a different answer (`typecheckDigest`: ok and the error codes) stops the run |
| Chrome | the staged case files and the call's mode; the judging sources, `runtime-oracle.mjs`, `packages/cli` (bin, lib, scripts, lockfiles and its installed node_modules), the browser (`browserKey`: its build directory's files), the oracle lockfile, `installedKey` | the first hit of a process runs fresh in the same oracle call; Chrome can flake under load, so a difference drops the cache for that call, runs every hit fresh (`cached: false`) and is listed in `spotMismatches` |

`installedKey` is what is really installed, not only what a lockfile asks for: Node's version, the runner's `FUZZ_PAUSE_MS`/`FUZZ_FINAL_MS`, and a stat walk (`treeStat`: every file's path, size and mtime, symlinks followed) of both installs' `node_modules`. It costs about 0.2 s a run. The runtime and Chrome keys hold the record sources, not the generator or the judges: a record is raw evidence, classified fresh on every run, so a generator that grows keeps the records of every program it still writes (a misuse grid after a generator change: 20,754 hits, outcomes identical, 617 s to 299 s, 2026-10-29). The neutrality baseline keys on every non-test module (`codeHash`), since its rows are classified. What no key holds is premise, not cache: the checker's absence from the runtime and Chrome keys rests on Solid's answer not depending on it (the Chrome cache is for confirmation only, above). Measured on 2026-10-28 with the ten dead-code false-positive repros fixed by #128: the pre-#128 checker and main disagreed on 7 of them (violation against uncertifiable), and Chrome's runtime records were identical on all 10. When the cache holds every program's records no Vitest batch runs, so the matrix gives the workers' share to the checker (`--concurrency` plus `--workers`: the same budget). Chunks are pipelined: one chunk's fast path runs while the next is type-checked and checked (`prepareEntries` and `finishEntries`, the two halves of `evaluate`), so neither pool waits on the other.

**Running the gate.** It is short now (one checker run is about 28 ms), so it runs at normal priority under the machine's heavy-job lock, like a build, not under the background clamp: `sc-heavy node scripts/fuzz/matrix.mjs --out <fresh> --seed 1 --per-cell 20 --concurrency 6 --workers 8 --baseline <matrix.json>` (normal priority runs on the performance cores; the background clamp pins a process to the efficiency cores). After a checker fix the warm cache leaves only the checker to run.

`--confirm-with-chrome` runs, per cell, up to `--chrome-sample` (3) agree programs, up to `--chrome-false-clean` (4) false-clean programs, up to `--chrome-other` (2) recall-gap and not-fired programs (a not-fired program Chrome fires is a Happy DOM gap) and every wrong-rule program in Chrome and records `same`, `differs`, `not-fired-in-chrome` or `chrome-inconclusive` beside the fast verdict. `--shrink` reduces the smallest Chrome-confirmed false-clean program of each cell (the control is the legal twin) and reconfirms the minimum in Chrome. Output: `matrix.json` (per cell counts, per binding and layer counts, per-seed verdicts, Chrome summary, minimum), `matrix.md`, `programs.jsonl`, `repros/`.

**Gate.** A cell's program seeds depend on the run seed, the code, the context and the index only (`cellSeed`), so a baseline and a later run with the same `--seed` and `--per-cell` judge the same programs. The gate fails (exit 1) when a judged program leaves `agree` for another judged outcome or enters `false-clean`, or a baseline cell is missing; it names the seeds that moved. `typed-away` and `harness` are not verdicts, they are what a loaded machine produces: a program that moves out of one of them is reported as "baseline unjudged" and never fails the gate, and a program that moves into one is an "infrastructure warning" (the run is suspect), also not a failure. A current run in which more than half the programs are typed-away or harness is refused (exit 2). Different seeds, per-cell counts or generator versions are refused (exit 2). A cell where the checker improved is reported, not failed.

## The legal-context matrix

`node scripts/fuzz/legal.mjs --out <fresh> [--per-cell N | --grid] [--confirm-with-chrome]` is the misuse matrix's twin for false positives. Each template's `legal` contexts (misuse.mjs) place the same call where it is correct Solid: a write in a handler, a timer or an effect apply; `onCleanup`, `createEffect`, `useContext` and `onSettled` in an owned body; a strict read in a memo, a compute, JSX or `untrack`; `flush`, `resolve` and an action call in a handler; and a store write through its draft or through the read proxy inside its own setter (`legalVariants`). A program is judged at its site:
- `typed-away` or `tsc-overlap`: as in the misuse matrix (a violation on code tsrs rejects is `tsc-overlap`);
- `not-legal`: the runtime reports the code, so the template is wrong there;
- `false-positive`: a violation covers a site the hit ledger shows ran, and the runtime reports none of its rule's codes;
- `unexecuted`: the site never ran;
- `disturbed`: the program threw or halted;
- otherwise `uncertifiable` or `clean`.

A legal program whose JSX reads a pending value renders its view under `<Loading fallback={0}>` (misuse.mjs `legalLoading`: PENDING_ASYNC_UNTRACKED_READ's `memo` cell, STRICT_READ_UNTRACKED's `latest`/`is-pending` in `memo` and `jsx`). Without it rc.17 reports ASYNC_OUTSIDE_LOADING_BOUNDARY, advisory but placeless, which `disturbances` counts, so a program with a violation at its site was `disturbed` instead of judged (60 lg-recall programs of the 644bd1a81 run, the `cb-*` forms of PENDING_ASYNC_UNTRACKED_READ `memo`). The fix moved lg-base 168, lg-src 264, lg-combo 524 and mx-combo 920 programs (the combinations that draw that cell as an extra) and 1,410 of lg-recall; `latest`/`is-pending` take no `render-compute` cell (a render effect in the body, which no JSX boundary covers; 48 programs).

Chrome rejudges the candidates on the twin with its ledger, and a confirmed one exits 3 (stop and report); it also rejudges up to `--chrome-sample` (2) programs per cell of each other outcome (`clean`, `uncertifiable`, `unexecuted`, `not-legal`) and lists the ones it judges otherwise (`chromeDiffers`: a clean program Chrome reports the code for is a template that is not legal). Codes whose legal form needs more than a context (a provider, a settled async value, a non-sync option) have no `legal` list.

## The recall axes

`--recall` (`matrix.mjs`, `legal.mjs`; `make fuzz-focus FUZZ_GRIDS=mx-recall,lg-recall`) adds the shapes real code writes and the base grids do not draw, each one a way the checker can lose a defect (most are listed in `docs/open-work.md` as known misses; the grid makes each a measured cell the gate can hold). | value bindings | a `let` or `var` alias, a conditional, an identity call's result, a literal with a spread, a computed key or a getter, a member of a local literal, a destructuring default, a nested pattern, an array slot |

**Mutation mode.** `node scripts/fuzz/mutation.mjs --out <fresh> [--recall] [--codes A,B]` pairs every misuse shape with the legal program of the same shape (the template's first legal context that takes it) and runs the checker alone on both. `distinguished`: a claiming violation on the misuse and none on the twin; `declined`: only an uncertifiable one; `static-miss`: nothing on either, the checker reads them alike (`certified` when the misuse file has no uncertifiable finding at all); `legal-flagged`: a claiming violation on the twin. No runtime runs, so a static miss is a candidate: the misuse grid says whether Solid reports the code there.

**Twin consistency.** `node scripts/fuzz/twins.mjs --out <fresh> [--codes A,B] [--contexts a,b] [--grids legal,misuse] [--recall] [--sample <fraction of groups>]` (`make fuzz-twins CODES=…`) runs the checker alone on the grids' twins: the programs of one code, context, variant, binding, callback form, mount and source that differ only in the layer around the site. Every layer the grids draw runs its body once, in place, synchronously (`TWIN_LAYERS` says how, layer by layer; a layer nobody classified stops the check), so twins do the same thing at run time and may differ in certainty, never in what they prove. Per group and per rule that claims a runtime code, a twin's answer is `violation` (anywhere in the file), `uncertifiable` or `none`, and a group is flagged when one twin is a violation and another is `none`, or, in a legal grid and for a rule that claims the cell's code, `uncertifiable` (the program is legal by construction, so the proof is the suspect). A misuse violation beside a declining twin is the fail-closed direction and is not flagged; a legal violation of another code's rule beside a declining twin may be a real defect of that code with a recall gap, and is not flagged either. Differences the execution model justifies go in `ALLOWED`, each with its reason (empty: none was needed). `--recall` takes a cell's base shapes with its recall shapes, since a base context's recall layers have their `none` twin in the base grid; `--sample` keeps whole groups. The type checks come from the type-check cache the grids fill. Output: `twins.json` (summary, flagged groups with every twin's layer, id and answer, by cell and by violating layer), `twins.jsonl` (each program's answers and findings); exit 1 when a group is flagged. `--from <earlier --out>` judges a recorded run again from its findings (no checker). ## The census

## The witness oracle

## The packages profile

`--profile packages` gives a program one or two exports of a generated dependency package, `fz-lib`, so the fuzzer tests how the checker reads dependency source (ADRs 0291, 0297, 0300). The same tree, host and disposition machinery builds the program; the helper layer is an export of the package. `package.mjs` is the single place that says what each behaviour does at run time (call the callback inline or N times; in `setTimeout`, `queueMicrotask` or `Promise.then`; under `untrack`, `runWithOwner(null | getOwner())` or `createRoot`; pass it to `createEffect`, `createMemo`, `onCleanup` or `onSettled`; return it, a wrapper of it, or `{ cb }`; store it in a module variable, array or object, with or without its owner, for a second export, `fire`, to call later; never call it) and in which export form (named, arrow, default, an index re-exporting `impl.js` by name, renamed or `export *`, a class method, a static method, an object method, a namespace import). The generator knows each behaviour, so each shape's runtime truth is determined; `packages-seeds.mjs` pins sixteen of them and `node scripts/fuzz/packages-check.mjs --out <fresh>` runs them through the fast path and exits 1 when the runtime contradicts one.

* **Layout.** The package is real ESM with `.d.ts` typings and a `package.json` of `type: module`, `peerDependencies: { "solid-js": ... }` and an `exports` map (`types`, `default`), the shape the checker selects (ADR 0291). It imports `solid-js` from the program's install, never its own copy. A case holds it as `node_modules/fz-lib/` and only the exports the program refers to; the checker and the type check see it below the case's work directory, the fast path stages it beside `App.tsx` (the Vitest config inlines `fz-*` so the dev build of `solid-js` is the one instance), and `oracle.json` names it in `packages`, which `runtime-oracle.mjs` copies into the run directory's own `node_modules`. Nothing is written into the shared install's `node_modules`.
* **The checker runs as a user's run does.** A case with a package is checked without `--feedback-facts`: under a declared runtime target and build an ordinary analysis reads the package from source (ADR 0297), and the feedback mode `feedback run` uses does not. Chrome is the runtime only for such a case; its checker verdict is this run's, on the clean text, with the checker's run on the twin as the neutrality control (always on for this profile).
* **Reads.** A read payload is drawn only when every package export on its chain hands the callback's value back, so its witness can land.
* **Triage.** Uncertifiable results at the package call (SC9005 or SC9012) count as uncertifiable; with a runtime diagnostic they are recall gaps, not false cleans.

## Containers

`--profile containers` (or `--containers` on top of any profile, `disposal` and `owner-cleanup` among them) wraps expression statements of a generated component in a *container*, a place where code is written but runs elsewhere, later or not at all: an uppercase inner function never rendered, rendered as `<Child />`, handed to a slot (`props.slot?.(Child)`, a local object's method) or returned; a class instance field, static field, static block, method or constructor (constructed or not); dead code (`if (false)`, after `return`, a function never called, `false && f()`, with `true && f()` as the live twin). It also passes the callback of every primitive by name (`const`, `let` or a function declaration), rewrites calls as `f?.()`, `(f as typeof f)()`, `(void 0, f)()`, `(true && f)()` or `(f)()`, and puts an `await` before or after the payload of an async container. Every program type-checks with tsrs. A function-like container has an entry counter and a direct form (`f = h();`, `false && h();`) the glue counter of its call, so the ledger tells ran from not-ran (`containers` in `results.jsonl`: kind, use, `entered`); a violation at a payload site in a container that never ran is a `candidate-false-positive: unexecuted` (counted on every profile, containers included; see Unexecuted violations). The profile draws its base profile (mostly `disposal` with the cleanup handle called now or later) from a stream of its own, so every other profile's seeds are unchanged. Not built: a callback imported from another generated file (a case is one `App.tsx`). Event handlers passed by name are the recall grids' `HANDLER_CONTEXTS` (below), not a container.

## The disposal profile

`--profile disposal` (`disposal.mjs`) builds a write that runs while an owner is disposed, the case rc.17's owned-scope write guard exempts (`disposalDepth > 0`) and an action call or a later run of the `onCleanup` handle does not. The host is an owner the driver can dispose (a `Show` a button toggles, a memo or effect a button reruns, a `createRoot` whose disposer a button calls); the cleanup keeps its handle discarded, kept, called at once or called later; a chain of wrappers (`runWithOwner(captured | createOwner() | null)`, `createRoot`, `untrack`, an IIFE, `forEach`, a helper, a timer, a microtask, a promise callback, an async function, `try`/`finally`, `flush()`) sits around the write, which is a signal setter, a store setter, `refresh(memo)` or an action call. Controls put the same chain in a component body (the write throws) or an event handler (legal). Cleanup evidence (did the driver really dispose the host, did the handle run) is in `results.jsonl` (`cleanup`), so a write that never ran under disposal proves nothing. `disposal-seeds.mjs` pins the known shapes with the runtime's answer for each; `node scripts/fuzz/disposal-check.mjs --out <fresh>` runs them through the fast path and exits 1 when the runtime contradicts one.

## How the evidence works

* **Sites.** Every payload read or write is a site. Its line is where its call is written.
* **Witnesses.** A site carries the page text that shows it ran and landed: a write to its own probe signal shows its unique value; a read's value reaches a sink signal or a rendered child. A site without a witness is never evidence of silence. Decoy constructs (a tracked memo read, a write in an apply, a write in a handler) are legal by construction and have witnesses too, so a violation on one is a candidate.
* **One component per page.** A thrown dev error halts reactivity for every root on the page, so a second component would hide or fake the first one's behaviour. The default is one component; `--components` is for experiments.
* **Disturbance.** Any throw, `REACTIVITY_HALTED`, or runner failure makes the other findings of that program inconclusive.
* **Same driver both sides.** The fast runner repeats the oracle's two passes of DOM events on every element, then clicks the plan's buttons and reads the witnesses; the oracle runs the same events and the same plan as scenario steps (`oracle.json`).
* **Signature.** The identity of a finding is its rule plus the construct path from the component to the site (host, closure forms, defaults, helper form, IIFE/forEach/map) and what the program does with each closure on that chain (called, returned, stored, passed to a helper of some form, called from a handler). Names, values and the rest of the file are ignored.

## The hit ledger

Every place the runtime can execute is counted. `print.mjs` emits two texts from one tree: `text` (clean, what the checker reads and what an owner reads in a repro) and `runText` (the twin: type check, Happy DOM, Chrome). The twin has `(__h(N), expr)` on each payload site and each *glue* call (every other emitted call: `m1()()`, sinks, memo accessors, primitives; only the top of a call chain is counted), `__h(N); ` before a statement that is itself a counted call, `{ __h(N);` at every function entry, and the counter's source after the last line, so no line moves. The counter touches no Solid state: it increments `globalThis.__scHits` and mirrors the counts as JSON into a plain-DOM `<output id="sc-hits">` outside `#root` (one pixel, transparent: the oracle's `wait-for-selector` needs it visible). The fast runner reads the global and polls until it is still (quiescence); Chrome reads the last two `#sc-hits` checkpoints, which the twin's `oracle.run.json` adds as steps.

A site is judged by two separate facts: `ran` (its counter is above zero) and `landed` (its witness text is on the page). A payload with a witness needs `landed`; a site with none (a glue call, a void payload) is judged by `ran`; a site that ran and did not land is inconclusive. A finding on a plumbing line (no payload site on its lines) is judged by the glue calls on them, replacing "the finding spans no site of interest". A payload site that never ran, placed in the ledger, on a quiet page whose host ran, is a `candidate-unexecuted`; the rest of the never-ran rows stay `inconclusive`. Every inconclusive item carries a `why` (`never-ran`, `ran-not-landed`, `no-witness`, `disturbed`, `perturbed-run`, ...). `results.jsonl` rows carry a `hits` summary per program.

### Neutrality

The counters must not move anything the fuzzer judges. Four checks, none needing Chrome except the last:

1. `strip(runText) == text` (`hits.mjs stripInstrumentation`, checked when the case is built; a failing program is inconclusive `not-neutral`).
2. `--control`: the clean text runs in the same engine and the (code, line) diagnostics, throws, witness texts and failure phase must match; the checker also runs on the twin's text and its (rule, kind, line) findings must equal the clean ones. A difference makes the program inconclusive `perturbed-run`.
3. `node scripts/fuzz/neutrality.mjs --seed 1 --count 300 --profile <p> --control --out <fresh>`: the same seed range with and without instrumentation (`--no-instrument` is the baseline mode of `run.mjs`). Only an `inconclusive` verdict may move, and only to a resolved one; any other change exits 1. It also reports how many findings that used to span no site now map to one. `--baseline <results.jsonl>` reuses a recorded baseline from the same checker; `--baseline a --candidate b` compares two recorded runs.
4. Chrome: the oracle runs the checker on the twin; its findings must equal the fast pipeline's clean ones, else `instrumentation-perturbed-checker` (inconclusive, `chrome-inconclusive`).

Observation: the checker reports nothing on `(f(), m1()())` as a statement in a component body where it reports `m1()()` written plainly (the comma expression hides the read). The counters avoid the form for that reason (statement counters); the gap is the checker's, and is recorded in the report that added the ledger.

### Speed

Nothing here changes a verdict (the acceptance run compares them): the fast path runs in one long-lived Vitest host, whose per-file environment is the isolation (`fast-daemon.test.mjs` has a program leave a global, a document attribute, a prototype property and a halted signal runtime, and the next must find none); its pool is `vmThreads` (a fresh V8 context per program; `FUZZ_FAST_POOL=forks` for the old one), which on 2026-10-29 cut a cold misuse grid's evaluation from 334 s to 127 s and a legal grid's from 122 s to 54 s (with batched type checks), every outcome, detail and Chrome verdict identical, the records differing only in an uncaught throw's kind (`window-error` for `node-uncaught`); type checks share one `tsrs -b --force` per batch (`createTypecheckBatcher`; `--no-typecheck-batch` for one process each), its answers rewritten to what a lone `-p` run prints and any unplaceable line rechecked alone; `--concurrency` (checker and type check) defaults to half the cores and `--workers` (Vitest) to twice the cores, since a program mostly sleeps on timers (on the virtual clock, the default: one a core); the neutrality baseline is cached under `--cache-dir` (default `$TMPDIR/solid-checker-fuzz-cache.noindex`) keyed by generator version, program, checker and type-facts sha256, the fast install's lockfiles and the hash of this directory's judging sources, so a later round re-runs only the instrumented pass (`--no-cache` to disable); `--order failing-first` puts what mismatched last time first and `--stop-on-mismatch` ends a round at the first mismatching chunk.

A shrink with `--control` asks for the neutrality control of each reduction it accepts, not of every candidate it tries (the control can only turn a verdict into `inconclusive`, so the answers are the same; `--shrink-control each` restores the old rule), shrinks its false-clean groups in a pool (`--shrink-jobs`) and reconfirms their minima in Chrome in one call. Chrome runs a case's clean control beside its twin in one oracle call, and runs a case that ended in `browser close timed out after N ms` once more. The fast path runs on a **virtual clock** (`fast/virtual-clock.mjs`; `--real-clock` restores the wall clock, the behaviour before it existed). The program's `setTimeout`, `setInterval` and their clears run on a clock the runner advances, so the runner's waits (60 ms after the render, after each pass of events and each click, 150 ms twice, 50 ms ticks of the hit-ledger settle) keep their lengths in virtual time and cost no wall time. It keeps Node's delay rules (a delay under 1 ms is 1 ms), the order of timers (expiry, then creation), a chain of 0 ms timers advancing a millisecond a link, the real microtask queue drained between two timer callbacks, and a throwing callback reported as an uncaught exception with the timers after it still run. It does not model: anything that waits on real time or I/O (`setImmediate`, `process.nextTick`, `Date`, `performance.now` stay real), a program slow enough that a real timer would have fired late (the real clock's verdicts depend on the machine there, the virtual clock's do not), and host timers that do not go through `setTimeout`/`setInterval` (`requestAnimationFrame`). A timer chain runs for the virtual length of the wait, as a real chain runs for its wall length, so a chain of 0 ms links runs one link a virtual millisecond. The generator emits `setTimeout(f, 0)`, `queueMicrotask`, `Promise.then` and `await` only. Equality with the real clock was measured, not argued: 15 profiles x 300 seeds, every row (verdict, items, hit counts, control) identical (`compare-runs.mjs`; `neutrality.mjs` over six of them exits 0 under both). **Chrome is never on it**: the oracle runs the real browser on its real clock, for confirmations and for the rerun of a shrunk minimum; the flag changes only the Happy DOM fast path, and a verdict Chrome cannot confirm stays unconfirmed.

`node scripts/fuzz/compare-runs.mjs <run A> <run B>` is the equality check for any of the above (every row but the wall times, the findings, the summary counts and the shrunk minima byte for byte). `--unexecuted-moves` compares two runs of the same seeds from before and after `candidate-unexecuted` existed: a row may differ only by an `inconclusive: never-ran` item that became a `candidate-unexecuted` one (listed as a move), and any other difference fails.

**A finding that claims the runtime is silent** (the unwindowed hint, ADRs 0443, 0530) is judged like any other until `window.mjs` measures it: the control run reads one signal per counter, rc.17 warns on that read exactly when a strict-read window is open there, and silence excuses the finding only where a counter on its lines ran with none open. The hint text moving makes the finding judged again, never quietly excused.

### Cost and throughput

Measurement only: no row, verdict, cache key or finding reads it, and with `SOLID_CHECKER_FUZZ_PERF=0` none of it is written (the rows of mx-base and lg-base for NO_OWNER_CONTEXT were byte-identical with it off and on, and mx-recall's 18,655 rows across three runs, 2026-11-02). Each grid writes `costs.jsonl` beside `programs.jsonl` (per program: checker wall time; from the Rust executor's `wait4` on Linux its CPU time, peak RSS and block writes, a warm check's null as the daemon's use is not the client's; role decisions with `--role-log`), `cost.json` (the checker's p50/p90/p99, the slowest (code, context, layer, variant) cells, every program over `--budget-ms` 1000 or `--budget-mb` 500) and `profile.json` (generate, evaluate, judge, Chrome, runtime differential, shrink and write times, and the pipeline's busy totals). `focus.mjs` samples /proc/stat and /proc/diskstats every 250 ms in a worker and prints a `perf <unit>:` line per unit: programs/s, the phases with fold and prune, checker p50/p99, CPU busy and iowait, idle stretches (at least 75% of the cores idle for `--idle-stretch-s` 10 s, named by the unit they fell in or the gap between units) and disk MiB per program (the VM's disks, aggregate: other processes count, tmpfs does not). It writes `<unit>/perf.json` and `<out>/perf.json`.

`node scripts/fuzz/perf-compare.mjs <old run> <new run> [--threshold 0.2] [--floor-ms 20] [--floor-count 2]` (and `focus.mjs --perf-against <run>`) compares per unit programs/s, checker p50 and p99, and the over-budget count, and flags a metric more than the threshold worse (exit 1). Runs that differ in codes, seed, selection, checker mode, budget, cores, a unit's programs or sample, or a unit's cache state (each stated: none, cold, warm, mixed) are not comparable (exit 2), never a pass: a cold runtime cache ran mx-recall NO_OWNER_CONTEXT at 75 programs/s, a warm one at 121-132.

### Unexecuted violations

ADR 0458: a violation at a site no execution reaches is uncertifiable, so the checker reporting one is a false positive. Five of them were found by a person reading `inconclusive: never-ran` rows. Now the run counts them (`summary.json` and `findings.json` `unexecuted`: candidates, programs, confirmed, by status, by basis, groups).

* **Candidate** (`candidate-false-positive: unexecuted`, verdict and item kind `candidate-unexecuted`, `unexecuted.mjs`), on every profile and with no flag. A violation of a rule a runtime diagnostic can contradict, whose payload sites the ledger shows at counter zero, each placed in the ledger, with the page quiescent, a function enclosing the site entered, and no disturbance. Its `bases` say why: `dead-code` (below `if (false)`, after `return`, in `false &&`), `container-not-entered`, `function-not-entered`, `in-default`, `skipped-in-entered-function`. A site that ran, a finding on a plumbing line (judged by glue calls), a site the ledger cannot place stay `inconclusive`. The verdict ranks under `recall-gap` and above `inconclusive`, so only a row that was `inconclusive: never-ran` moves. A candidate never exits 3.
* **Confirmation** (`--confirm-with-chrome`). Each candidate's program runs in Chrome with the counters, and the fast path runs its clean-twin control. `confirmed-unexecuted` (exit 3, shrinkable) needs every condition of `deadsite.mjs` on Chrome's records, plus no diagnostic of the rule's codes anywhere. Anything else is typed: `refuted-by-chrome` (`chrome-ran`, `chrome-diagnostic`) or `chrome-inconclusive` (`chrome-failed`, `chrome-checker-differs`, `rule-code-reported`, `instrumentation-perturbed-checker`, a disturbance, or `conditions-unmet` with the conditions). The conditions are the old dead-site ones with two narrowings: the closed grammar admits the containers of `container.mjs` (`closedGrammar(program, { containers: true })`, `comp-prop` excepted since the caller supplies the prop), and a site the text itself skips (`lexicallyDead`) needs neither the grammar nor the no-throw reading, since no driver and no throw is behind a skip the text makes. Every other site keeps every condition.
* **`--dead-site`** now means the strict confirmation: the strict grammar (no container) and no waiver, the conditions as they stood before. It is a mode, not a second path. Folded, not kept as its own subkind, on this evidence: the strict conditions are a subset of the default ones, so it cannot confirm anything the default does not; and it confirms none of the five known false positives (m1-m5, all containers; each ends `closed-grammar`), so as a separate verdict it would stay silent where this was built to speak. It stays only as the way to ask for the smaller claim.
* **Not covered.** A finding on a plumbing line stays `inconclusive`, so two of the five original programs (a createEffect call after an `await` in a component never rendered) are not flagged in that shape; their minimal forms with a payload site are. A shrunk repro keeps its witness probes (Chrome waits on them) but is not rerun in Chrome.

## The role log and saturation

ADR 0533. A grid's findings say what it found, not whether its programs reached checker code the earlier grids never ran. The checker records which arm of its role and owner classifiers answered each decision when `SOLID_CHECKER_IR_ROLE_LOG` names a file (appended to) or a directory (one `roles-<pid>.jsonl` per checker process, so a grid's concurrent checkers never share a file). One JSON line per decision: `k` (`read`, `write`, `action`, `role`, `owner`; `unframed` for an arm hit outside one), `f`/`s`/`e` (the site), `role` (or `rule` and `ctx` for an owner answer), `arm` (the last tagged arm that returned the final answer; null when an untagged path did), `arms` (every tagged arm passed), `default`, `silent` (no rule reports the answer; absent for `role`, which feeds both rule families). An arm is a `role_arm!("<file stem>.<name>", …)` or `arm_id!(…)` literal in `rust/crates/solid-reactive-ir/src/execution_role*` and `owners/`; `default` marks a non-reporting answer given for want of a proof. The log changes no verdict and costs one atomic load per hook when unset.

```bash
# The focus loop with the log: <grid>.roles.jsonl per grid, <grid>/roles.json per grid, <out>/roles.json for the run
node scripts/fuzz/focus.mjs --codes A,B --checker-bin ... --typefacts ... --role-log [--roles-against <earlier roles.json>]
# By hand, any grid (the log beside the fresh --out)
SOLID_CHECKER_IR_ROLE_LOG=<out>.roles.jsonl node scripts/fuzz/matrix.mjs --out <out> ...
node scripts/fuzz/roles.mjs [--against <roles.json>] [--out <roles.json>] <out> [<more grid dirs>]
```

`roles.json`: `armsKnown` (the inventory, read from the source; a duplicate id or one under another file's stem fails the fold), `armsHit`, `neverHit` (the audit queue: no program reached them), `notInInventory` (a stale build), per arm `passed`, `answered`, `programs`, `silent`, `roles`, `kinds`, and `saturation`:

* `yield`: findings per 1,000 programs (`false-clean`, `wrong-rule`, `false-positive`), fast-path candidates and Chrome-confirmed (`chrome.status` same).
* `growth`: arms this run hit that `--against`'s run did not (null without one).
* `silentByDefault`: decisions a `default` arm answered with a role no rule reports. Each is a place where silence is a default, not a proof.

A slice is saturated for its axis when its new programs raise none of the three (0 confirmed, 0 new arms, a flat silent-by-default count); its axis then belongs in the smoke set only. A decision counts once per program and site, so a program the checker ran twice (a confirmation, a twin) counts once. The program is the directory the checker ran in (`roles.mjs programOf`): the Rust executor's slot is `slots/<n>/<id>/`, renamed to each program it takes (`SlotDir`, its files kept). Before, a slot was one fixed directory, so every program of a grid folded as one: decisions of different programs on a slot deduplicated against each other, per-arm program counts were 0, and the decision count moved with the scheduling (refolding the lg-recall FLUSH_IN_EFFECT_CALLBACK grid's logs, 5,034 programs: 26,214 and 26,118 decisions on two runs under the old names, 303,593 on both under the new). A log from before folds as it did, its decisions counted as `unattributed`. A grid's log is one file every checker appends whole lines to (a directory would take an inode a program, ADR 0519); a line two processes interleaved is `malformed` in `roles.json`, never folded. The raw log runs to about 23 KB a program (336 STRICT_READ_UNTRACKED programs: 7.8 MB), so a recall grid takes `--split-codes`, and `--prune-cases` deletes each log once folded. Overhead on that grid, release checker, 4 at a time: 2,642-2,802 ms without the log, 2,681-2,785 ms with it (three rounds each), every finding the same. The log covers the classifiers, not the whole engine: region coverage (`cargo llvm-cov`, ADR 0533) is the stronger measure. When it is not installed (no `llvm-tools-preview` on the pinned toolchains, no `cargo-llvm-cov`, as on 2026-11-01), the arm log substitutes for `execution_role/` and `owners/`: `neverHit` is the uncovered-arm queue and `growth` the per-PR delta, with two limits: an arm is a return, not a region (code between two returns is not seen), and `local_access.rs` and `interproc/` carry no arms. To get region coverage later: `rustup component add llvm-tools-preview --toolchain 1.99.1`, `cargo binstall cargo-llvm-cov`, a `RUSTFLAGS=-Cinstrument-coverage` build in its own target directory, `LLVM_PROFILE_FILE` set for a smoke run (about 2-3x slower).

## Equivalence mode

`node scripts/fuzz/equivalence.mjs` is metamorphic testing. For each generated program it runs the checker on the program and on `--equivalence N` variants (default 3), each the program under **one** rewrite that does not change what it does at run time (`rewrite.mjs`). The verdict at every site of interest is compared across the two. The rewrites are equivalent by construction, so a different verdict is a checker placement path that handles one spelling and not the other; no runtime is needed to find it, and Chrome only says which side is right. It takes the generator flags of `run.mjs` (`--profile`, `--seed`, `--count`, the tool flags), works with every profile, and leaves `run.mjs` and its verdicts untouched when it is not used.

Rewrites (`rewrite.mjs` states each one's soundness argument beside it; none moves code into or out of an effect, `untrack`, a component body or an async boundary, so none depends on timing, owner or tracking): `rename` (alpha-renaming of same-file names), `extract` (`const t = e;`, `const t = e; return t;`), `block`, `if-true`, `try-finally`, `iife` and `outline` (a statement in a synchronous IIFE, or a helper declared and called at once), `inline` (the reverse of `iife`), `callform` and `accessor-form` (`(f)()`, `f?.()`, `(void 0, f)()`, `(f as typeof f)()`, `(true && f)()` on a function name and on a signal accessor or setter), `declform` (function declaration against `const` arrow, only where hoisting is not observable), `reorder` (a closure declaration swapped with an independent neighbour) and `dead-decl` (an unread declaration). A wrapper prefixes the first line of the statement and suffixes its last, so a one-line statement keeps its line. A variant is type-checked with tsrs and dropped (counted as `type-error`) when it does not pass. A subset of the places a rewrite fits is drawn from the variant's seed; `--rewrites a,b` and `--exclude-rewrites a,b` pick the kinds.

The **site map** is a tag: every site node carries its original id (`eqSite`) through the rewrite, and the variant's printed sites map back to the original's by that tag.

| bucket | meaning |
| --- | --- |
| `high` | a violation on one side and clean on the other, or two different rules. A user-visible difference. |
| `certainty-divergence` | uncertifiable on one side and clean on the other. The forms are equivalent, so the clean side claims a proof the checker cannot make on the other: a possible silent clean (fail-closed). `cleanSide` says which. |
| `low` | a violation on one side and uncertifiable on the other, or uncertifiable against another rule. Internal (ADR 0328). |

Each divergence is a typed `equivalence-divergence` with both programs (`divergences/<variant id>/original.App.tsx`, `variant.App.tsx`, `divergence.json`; `*.program.json` are the trees). Groups are keyed by rewrite kind plus the fine signature of the original site (`equivalence.json`, `divergences.jsonl`, `results.jsonl`). With `--confirm-with-chrome` one representative per high and certainty group (`--chrome-max N`, default 40) runs in Chrome, original and variant together: `violation-confirmed` (Chrome reports a defect the violating rule claims, so the other side misses it), `violation-contradicted` (the site ran undisturbed with no diagnostic: the violation side is a false positive, **exit 3, stop and report**), `defect-at-site` / `silent-at-site` (certainty divergences), `inconclusive`, and `unsound-rewrite` (the two Chrome runs show different diagnostics or witnesses: a fuzzer bug, **exit 5**; drop the rewrite with `--exclude-rewrites`). A run the driver could not finish (a throw halts reactivity and the next step finds no element) is judged one way only: a diagnostic it reached before the failure can confirm a violation or show a defect, but a missing diagnostic never yields `violation-contradicted`, `unsound-rewrite` or `silent-at-site`; those stay `inconclusive`, because the part that never ran could hold the diagnostic. A run in which no program was checked is refused (exit 2). `--shrink` (`--budget`, `--shrink-max`) reduces one program per high and certainty group while the same divergence holds, the rewrite applied at every place it fits (`repros/<hash>/`).

Equivalence mode does not make a rewrite a license to compare unlike code: a rewrite that is only equivalent under a condition (a name used before its declaration, a `return` in an IIFE) checks the condition and declines. Calibration: on a checker from before PR #128 (a violation at a site no execution reaches was reported), containers programs show `low` divergences between `if (false) { createRoot(f1) }` and the same statement outlined into a called closure; on main they agree.

## Rerunning a run's programs by id

A run with `--prune-cases` keeps no case directory, so `replay.mjs` has nothing to replay; its programs are generated again instead (each is a function of its grid's seed and shape). `node scripts/fuzz/rerun-ids.mjs <run dir> --out <manifest dir> [--outcomes harness] [--grids a,b] [--rerun-out <dir>] [-- <grid args>]` reads the run's rows (`<grid>/programs.jsonl` or, split, `<grid>/<code>/`), writes one id manifest per (grid, code) with each program's recorded reason, and prints (and writes as `rerun.sh`) the `matrix.mjs`/`legal.mjs --grid … --ids <manifest> --confirm-with-chrome` command for each, restricted to the codes and contexts the ids name. For the 644bd1a81 audit's seven harness programs (five mx-recall STORE_WRITE_OUTSIDE_SETTER `effect-cleanup-show` under the `dynamic` mount, two lg-recall REACTIVE_WRITE_IN_OWNED_SCOPE `handler` under `show-keyed`), in the VM: `node scripts/fuzz/rerun-ids.mjs /mnt/lima-colima/sc/runs/full-main-644bd1a --out /mnt/lima-colima/sc/runs/rerun-harness-644bd1a --grids mx-recall,lg-recall -- --checker-bin /mnt/lima-colima/sc/solid-checker/rust/target/release/solid-checker-rust --typefacts /mnt/lima-colima/sc/solid-checker/bin/solid-typefacts`, then `bash /mnt/lima-colima/sc/runs/rerun-harness-644bd1a/rerun.sh`.

## Replay

`node scripts/fuzz/replay.mjs --out <fresh dir> <dir|list> [...] [--confirm-with-chrome]` re-judges recorded programs with the current checker without regenerating their seeds: the recheck after a checker fix. An argument is a directory or a text file that lists directories (one per line, an optional label after the path, `#` comments). A directory is an item when it holds:

| item | files | what is judged |
| --- | --- | --- |
| pair | `original.program.json`, `variant.program.json` (an equivalence `divergences/<variant id>/`) | both trees rebuilt as cases, compared at the recorded sites by the site map; Chrome judges them as equivalence mode does |
| text pair | `original.App.tsx`, `variant.App.tsx`, `divergence.json` (a shrunk equivalence repro) | both texts, compared at the recorded lines; Chrome runs each text with the oracle's own driver |
| plain | `App.tsx` (a repro) | the checker's findings against the defect diagnostics Chrome reports in the file |

Any other directory is searched for items. Per item (`replay.jsonl`, `replay.json`, a line on stderr): the bucket now (`agree` when both sides agree at every recorded site), the bucket and Chrome status recorded with it (a pair reads them from its run's `divergence.json` and `equivalence.json`), Chrome's status now, `chromeCache`, and `fixed`. An item is `fixed` only when both sides agree on a violation and Chrome still reports a code its rule claims there; two clean sides agree but are not fixed. A plain repro is fixed when every defect diagnostic Chrome reports is covered by a claiming violation. Exit 3 when Chrome contradicts a violation (stop and report).

A plain repro whose violation Chrome shows no diagnostic of the rule's codes for (and whose rule a runtime diagnostic can contradict) is `violation-without-diagnostic`: a candidate false positive for a person to read. A bare text has no witness, so nothing shows the site ran; it is never a confirmation. `probes/store-setter/` holds the setter-extent cases: writes deferred out of the setter's callback (`queueMicrotask`, `setTimeout`, `.then`; the draft is closed, Solid reports STORE_WRITE_OUTSIDE_SETTER), the two shapes `docs/open-work.md` records as false positives (a closure defined outside the setter and called in it, an intermediate the store does not wrap), a read-proxy write in its own setter, and the legal draft write. A probe directory may hold `probe.json` (`{ witness: { selector, text }, steps? }`): Chrome runs the steps and reads the selector, and the text says the claimed effect happened (the store probes write the raw value into `#w` after the write). A violation Chrome is silent on whose witness landed is `false-positive-witnessed` (stop and report); one whose witness did not land is `violation-witnessed` (the behaviour backs a violation the runtime does not warn about); a false clean, or a silent program with no violation, whose witness did not land is `defect-witnessed`. `probes/stale-read/` witnesses the three stale reads rc.17 leaves silent (ADR 0443: an unnamed `mapArray` map function, a provider's `value`, a `runWithOwner` callback in a memo) by value: the witness is the updated text, so a stale read does not land it; each has a tracked control that does. `probes/flush-in-action/` (helper, IIFE, named closure; ADRs 0478, 0479) and `probes/alias-slots/` (a tuple slot read, an object-literal arrow's setter slot in a memo, and the legal in-setter write; ADR 0480) are the rediscovery probes of those fixes. The source axes' findings have probes beside the areas they belong to (`probes/{write,store-setter,action,strict-read,read-after-await,pending-async}/` `prop-*`, `context-*`, `module-*`; a probe's `helpers.ts` is copied beside its `App.tsx`), and the combination programs' has `probes/pending-async/effect-apply-read-beside-jsx-expression`. A probe's click must be idempotent (set a value, not add to it): the oracle clicks every element twice before the steps. Run them with `node scripts/fuzz/replay.mjs --out <fresh> scripts/fuzz/probes --confirm-with-chrome`. `probes/` is input, not a judging source: it is not in `codeHash`.

**Rediscovery.** `--baseline-checker <earlier solid-checker> [--baseline-typefacts <its solid-typefacts>]` judges every item with that binary too and marks the items whose judgement differs (`before`, `changed`; `CHANGED` on the line). A fix's probes must change against the binary from before it, and its controls must not: on `probes/store-setter`, main before ADR 0476 against the fix changes the three deferred writes and the two false positives, and not the two legal writes.

**Chrome cache.** `replay.mjs` and `equivalence.mjs --confirm-with-chrome` keep each Chrome record under `--cache-dir`, keyed by the staged case's files, the call's mode, the judging sources, `scripts/runtime-oracle.mjs` with the product scripts it drives Chrome with (`packages/cli/scripts`), the browser build and the oracle install's lockfile, so a recheck runs Chrome only on new programs. It is for confirmation only. The checker is not in the key, so a cached record's checker half is the run's that stored it: callers that judge the checker by Chrome's findings (`run.mjs`, `matrix.mjs`) do not use it. A cached answer is named on its row (`chromeCache: "hit"`, `[chrome cache hit]`), so it never turns a fresh disagreement into agreement unseen. Harness errors and pages that never loaded are not stored. `--no-chrome-cache` turns it off.

**Guarded reads.** PENDING_ASYNC_UNTRACKED_READ's legal contexts `{effect,render}-apply-guarded` (and `-closure`) put the read behind `if (v === 1) return;` with a constant compute, so the only run skips it: a false SC5001 there is a false positive (the legal judge counts a run-claiming rule at a site that never ran), and the site is otherwise unexecuted. `-guarded-rerun` makes the compute read a signal a button sets to 2: the apply runs again, the read executes after its source settled, and Chrome's STRICT_READ_UNTRACKED confirms the checker's SC1001 there (judged, the legal judge's `uncertifiable`: a violation whose code the runtime reports).

**Mount axis.** `--mounts root,child,show,for` (both grids, with `--grid`) also renders each program's component from an exported parent `P1`: plainly, under `<Show when={true}>`, or in a one-row `<For>` (misuse.mjs `MOUNTS`; the component is then not exported). A root program keeps its seed, id and text; another mount's id ends `-m-<mount>`. The first run (2026-10-29) found the false cleans and the call-result false positive of ADR 0506.

**Source axes.** `--sources <axes or sources>` (both grids, with `--grid`; default `local`) takes the values a misuse uses (a signal, setter, store, memo, action or async memo of the template's `setup`) from somewhere other than the misuse component (misuse.mjs `SOURCE_AXES`): `props` (an exported parent `P1` creates them and renders `<C1 w1={w1} setW1={setW1} />`; read as `props.w1`, a destructured parameter, through `merge({ extra: 1 }, props)` or `omit(props, "extra")`, through `M1`, which spreads its props on `<C1 {...props} />`, or as a read's value `w1={w1()}`), `context` (`<ValCtx value={{ w1, setW1 }}>` and `useContext(ValCtx)`, as an object or destructured), `module` (`helpers.ts` creates them at module scope or in a hook `useVals()`, destructured or as an object) and `async` (an async memo created in the parent: passed as an accessor, as its value, by context, or under the parent's `<Loading>`). rc.17 has no `splitProps`/`mergeProps`; `merge` and `omit` are its forms. A source applies only where it can (`sourcesOf`: async sources need an async value, props and context need none, a value source needs a bare read and a binding that keeps it at the site), is not crossed with the mounts, and a local program keeps its seed, id and text; another source's id ends `-s-<source>`.

**Combination programs.** `--combine` (both grids, with `--grid`) replaces each shape's program by a combination (misuse.mjs `buildCombo`): the cell's site, marked `primary` in `sites.json`, shares its component with one or two legal uses of other codes (each a site, in a legal context, bound directly) and, half the time, unrelated reactive code (a signal, a memo on it, an effect on the memo, a handler write, the memo in the JSX); its values come from a source drawn from those the shape takes, so a program can hold a parent, the component and `helpers.ts` at once; the parts' statements are interleaved. Every draw is the program's seed's; the id ends `-c` and the seed key `/combo`, so it composes with `--sources` and `--mounts`. The misuse grid judges the primary site and leaves out the findings on the other uses' lines (`others`, `detail.atOthers` lists their violations); the legal grid judges every use with its own code and takes the worst (`judgeLegalProgram`, `detail.sites`).

**Browser execution cache.** The grids (`matrix.mjs`, `legal.mjs`) pass `feedback run --execution-cache <cache-dir>/browser-execution` to Chrome confirmation (`browserExecutionCache`). That product cache reruns the checker on every case and keys only the browser half (Vite, Chromium, the scenario) on what it reads of the checker (the development models, the type error count), the sources, scenario, browser, tooling and harness, pinning every file Vite served (packages/cli/scripts/feedback-execution-cache.mjs). So a grid still judges this checker, and the oracle's stable staging path (`<install>/.solid-checker-runtime-oracle/<id>`) lets the key match across runs. Measured 2026-10-29: misuse grid 630 hits, 151 s against 639 s filling it; legal grid 206 s to 52 s; every outcome and Chrome verdict identical. `--no-cache` or `--no-chrome-cache` turns it off.

**Halted runs.** A generated case asks the oracle for its halt marker (`"haltMarker": true` in `oracle.json`): a second page module, outside the case's tsconfig so the checker never reads it, that appends `<output id="sc-halted">` when Solid reports `REACTIVITY_HALTED` or an error-severity diagnostic (rc.17 throws at the site of each; an `Errored` boundary that catches the throw shows its fallback with no error event, so the elements below it never render again: Fuzz audit run 41696018194 waited 12 s for a button its `errored` mount had swapped out), or the page has an uncaught error. Every click and witness step names it as its alternative (`X, body:not(:has(X)) > #sc-halted`, `haltable` in `hits.mjs`), so a wait for an element a halt keeps from appearing ends at once instead of after the scenario's 12 s timeout; with no halt the selector is `X`. `chromeRuntime` reads such a checkpoint as absent and the run as cut short (`failure.phase: "halted"`), so the partial-run rule stands: a diagnostic reached may confirm, a missing one never contradicts. The fast path needs nothing: on the virtual clock a wait costs no wall time.

## Run integrity

A run refuses (exit 2) when more than half its programs fail to type-check or the harness could not judge them (`harness`: a checker that would not start, a missing producer). A checker run whose premises say the harness's own entry (`main.tsx`, the oracle's event passes) withholds the event-handler proofs is recorded (`entryVeto` in `matrix.json` and `legal.json`, and a warning): with it, a handler context's results say nothing about the handler proofs. Before ADR 0477 every run was so: the entry dispatches its events after an `await`, which the dispatch veto did not credit, and an inline handler's write was uncertifiable.

A plan may list `edits` (`{ selector, text }`): the user types into an input before the clicks (the fast runner sets the value and fires `input`; Chrome `fill`s). `probes/uncommitted-input/` uses them: a stateful `value` binding rewritten over typed text by a sibling attribute's change (UNCOMMITTED_INPUT_OVERWRITTEN, which no rule claims; Chrome reports it unattributed, as its stack is all runtime frames), and two controls. Replay judges an unattributed diagnostic with no lines, and a code no rule claims as `unclaimed`.

## Not built (design notes)

What the 2026-11-03 reports proposed and these slices leave out, with the reason:

* **A thrown code past an async compute's await.** The throw only rejects the compute's promise: no diagnostic, no page error, so the runtime looks silent. `useContext` (NO_OWNER_CONTEXT, CONTEXT_NOT_FOUND) and `dynamic(..., { static: true })` in `memo-async*`/`effect-async*` throw and are reported by nothing, so they take no cell, legal or misuse (`ASYNC_FAMILY_PLACEMENT`). A legal cell there was measured with its site in a `try` and a marker after it; an oracle that observes the rejection would give these their misuse cells.

* **SSR host for SC7006, SC7007 and SC5003's `ssrSource: "client"`** (SC7005's is built: `ssr.mjs`). SC7006 (valid-use-server) has no runtime defect to observe: its claims are the pinned compiler's directive pass refusing or dropping a shape (a compile error, an export the server build never registers), so its oracle is that pass's own output, a compiler oracle, not a server render, and the compile errors are already the rule's audited source (ADR 0427). SC7007 (server-function-rich-argument) rejects on the client transport (`isJSONSafe` in `@solidjs/web/server-functions` before any request is sent): an oracle would call a server-function reference in the browser with each argument shape and read the rejection, which needs the server-functions build plugin to compile `"use server"` references and is the Chrome host's work, not the SSR host's. SC5003's `ssrSource: "client"` needs hydration (server render, then the client run on the server's HTML). Each is a host or a compile pipeline of its own; none is faked as an SSR diagnostic.
* **Lifecycle histories** (initial pending, settled before the mount, refresh, disposal before resolution, same and distinct flights). The settled-before-mount history is built (the pair grids' `show-later` × `async-*`, which found ADR 0518's family on a later mount); the others need controlled promise resolution in the driver (`oracle.json` steps that resolve a promise on a button), which the fast runner and the oracle do not share yet.
* **Package topologies as grid layers** (project barrel to package, package to package, conditional exports). The packages profile's machinery exists (package.mjs), but a package program is checked without `--feedback-facts` and its records are not the grids' (the executor's slot directories assume no `node_modules`): a grid layer needs the executor's `ordinary` path per program and a per-code census; left to the packages profile.
* **Multi-instance mounts** (`for-2`, the component rendered twice). The driver's selectors must match exactly one element (every `data-act` and witness is unique), so two instances need instance-numbered ids through the whole printer.
* **`<Ctx value={undefined}>`** (a provider element; the model has none) and **`createSignal(0, { unobserved })`** (its callback's owner is unmeasured): the `default-undefined` variant measures the same CONTEXT_NOT_FOUND silence.
* **Depth ladders per bounded walk** (helper chain 6, callback-prop forwarding 8, async helper chain 4, hook pass-through 4, leaf chain 3) and **open-boundary replay**: each needs the bound's exact value read from the checker's source per walk; the IIFE ladder (`DEPTH_FORMS`) stays the only one.
* **Fable's F0** (a declining rule in `judge` for CONTEXT_NOT_FOUND's owner obligations): another branch's work (`claude/context-fc-owner-handoff`).

## Known limits

* The fast path runs in Chrome (ADR 0512), with the fast runner's driving, not the oracle's (`feedback run`): the runtime differential (`--runtime-diff`) measures the two against each other per stratum, and the oracle still judges candidates. With `--fast-host happy-dom`, a false positive the fast path does not produce is not looked for in Chrome.
* One component per case, plus the parents and `helpers.ts` of the mount and source axes; a handler passed by name only in the recall grids' `HANDLER_CONTEXTS` (a `const`, a `function`, the bound tuple, a mixed caller), never a handler from another module.
* A program `tsrs` rejects is no recall evidence (invariant 1), so a defect the published typings catch is out of reach by design: the matrix records such programs as `typed-away`, and as `tsc-overlap` when the checker reports a violation on the rejected code. `twins.mjs` and `mutation.mjs` still skip them unchecked.
* A site that never ran, or ran without landing its witness, is `inconclusive` or an unexecuted candidate, never agreement. Sites in containers that never ran, programs that throw or halt reactivity, and diagnostics Chrome cannot place on a line limit what a run can say.
* `ASYNC_OUTSIDE_LOADING_BOUNDARY` is reported from the render root (`placeless`), and it is advisory: neither the matrix nor `run.mjs` counts the checker's silence on it.
* The instrumentation hides the read in `(f(), m1()())` from the checker; the counters avoid the form, and the gap is the checker's (see Neutrality).
* Packages: only the export forms and behaviours `package.mjs` lists; a read payload only through exports that hand the callback's value back; the checker's run is the clean text's, not Chrome's own.
* The matrix gate compares the same seeds and per-cell count against a recorded baseline of a given generator version; it says nothing about programs it did not draw.
* The fuzzer is operator tooling: it is not part of `make verify`, and the checker and its gates do not read it. Do not change the checker from inside a fuzzing session.

## Layout

| file | role |
| --- | --- |
| `model.mjs` | the construct tree and its validator (a small type checker for the node language) |
| `generate.mjs` | seed -> program: a payload (write or read) in layers (closures, defaults, IIFE, forEach/map, helpers), a host scope, a disposition |
| `print.mjs`, `emit.mjs` | tree -> the clean `App.tsx` and its instrumented twin `App.run.txt`, with the site table, glue (auto-sites) and hit ledger; an oracle case directory (`App.tsx`, `oracle.json` steps, `program.json`, `sites.json`, and the twin's files) |
| `container.mjs` | the containers dimension: wraps statements in places that run elsewhere or not at all (components, classes, dead code), passes callbacks by name, rewrites call forms; the ran/not-ran evidence per container |
| `hits.mjs` | the hit ledger: the counter's source, the strip, the readout parser, the per-site record, and the pure comparisons of the neutrality gate |
| `neutrality.mjs` | the regression: a seed range with and without instrumentation, verdict by verdict (`--profiles`, `--chunk`, `--order failing-first`, `--stop-on-mismatch`) |
| `fast-daemon.mjs`, `fast/serve.mjs` | the long-lived fast host: one Vitest process (Vite server, Solid plugin, transform cache) serving every batch; `--no-daemon` gives one process per batch |
| `cache.mjs` | the baseline cache of the regression and its mismatch history; the runtime and Chrome caches |
| `unexecuted.mjs`, `deadsite.mjs` | the unexecuted candidate (the ledger's proof), Chrome's judgement of it, and the confirmation conditions as code |
| `typecheck.mjs` | `tsrs -p ... --noEmit` against the published typings; a program that does not type-check is dropped |

## Phases

1. Generator, type-check, classifier, shrinker, dedupe, CLI. Unit tests: `packages/cli/node_modules/.bin/vitest run --config packages/cli/vitest.config.mjs scripts/fuzz`.
2. Rediscover this week's false positives on the pre-fix checker (ADR 0452 families), then confirm the fix clears them.
3. Sweeps on the current checker; confirmed findings go to the owner.
4. The hit ledger (phase A): the twin, ran/landed, glue sites, the neutrality gate. Unexecuted violations are counted, then confirmed in Chrome.
5. Speed: one long-lived fast host, a baseline cache, batched shrinking.
6. Owner and disposal profiles (phase C), then false cleans (phase D): the policy table and its drift test, the verdict tiers, the ledger, coarse dedupe, Chrome confirmation, focused shrink, exit status 4.
7. The misuse profile with the recall matrix and its gate; the packages profile; the containers dimension.

## Provenance

The shrinker's search loop (execution budget, seen-set of canonical candidates, validity filter before any run, sweep schedule, control hook, complexity ordering), its halving-width chunk removal, and the idea of weighted generation come from Solid's semantic fuzzer, solidjs/solid PR #3446 "test(signals): add experimental semantic fuzzer" (open, MIT), commit 030e77f2b, `packages/signals/tests/semantics/` (`search.ts`, `shrink.ts`, `complexity.ts`, `candidates.ts`, `generate.ts`). `shrink.mjs` carries the per-file note. That fuzzer interprets a scenario DSL against the signals engine and checks written rules; this one emits Solid source and compares the checker with the runtime, so the generator, the candidate families, the oracle and the dedupe differ (`footprints.ts` dedupes by an engine work ledger; a checker finding has none, so the construct path replaces it). The fast path's runner and shims are ported from the Happy DOM experiment (`happy-patched-runner.tsx`, `happy-dom-fixes.ts`), without its corpus-specific doubles.

## The pattern lane

`patterns.mjs` runs `patterns/`, the audits' programs verbatim, in Chrome and the checker. `open-defects.json` lists what fails today: every gate prints it, a listed failure does not fail a run, an unlisted one does, and so does a listed program that passes, until its entry moves to `rediscovery.json`. `make fuzz-patterns` is strict; `make fuzz-smoke` reports the lane and leaves its verdict to that target, since another machine's Chrome may differ.
