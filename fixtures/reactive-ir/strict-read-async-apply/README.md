# strict-read-async-apply

**Claim (ADR 0467).** An effect or render-effect apply that reads an async source makes rc.17's `read()` throw `PENDING_ASYNC_UNTRACKED_READ` when the run meets the source pending, before the strict-read warning (`@solidjs/signals@2.0.0-rc.17` `dist/dev-shared.js:5320-5325`, `:5441-5446`); a run that meets it settled warns `STRICT_READ_UNTRACKED`. Which one a run meets is timing: `ApplyReadsAsync`, `RenderApplyReadsAsync` and `RenderApplyReadsAsyncRendered` throw, while `ApplyReadsAsyncRendered` (the mount waits on the rendered read), `ApplyComputeReadsAsync` (the compute waits on it) and `ApplyComputeWaitsOnOtherAsync` (the compute waits on another source) warn, though each apply is written alike (rc.17 fast path). Nothing local orders the first run against the source's settling (a held mount anywhere above, a compute that waits, a later run), so the strict read stays the claim (`SC1001`, violation, with a sentence naming the pending case) and `pending-async-unsuspendable-read` claims no apply read. Controls: a sync source in the apply (`ApplyReadsSync`, `SC1001`) and an async read in the body (`BodyReadsAsync`, `SC5001` only). Stub: the rc.9 typings of `async-boundary-call-attributed`, rc.17 package manifests.

ADR 0504: `main.tsx` mounts each component by a module-scope `render`. Where a render effect's first run is proven to meet the source pending (`RenderApplyReadsAsync`, `RenderApplyReadsAsyncRendered`: the first run is on the call, before any JSX renders), the read is `pending-async-unsuspendable-read` (SC5001) and the strict read is not reported. ADR 0505: `ApplyReadsAsync`, a user effect whose first apply runs in the tail flush of the first `render` (a static tree, nothing else in the body, nothing before the render), is SC5001 too. `ApplyReadsAsyncRendered` keeps SC1001: it is not the first render, and its rendered read may hold the flush; so do a compute that reads or waits, the unmounted `UnmountedApplyReadsAsync`, and the review's negatives `ReadAfterCall` (a call before the read may throw first) and `BodyReadsFirst` (the body read throws before the effect exists), and `RenderApplyGuarded`, `RenderApplyGuardedClosure` (the first run, or the closure it calls, returns before the read). `SharedClosure` (two effects call the closure) proves neither: its closure read has no async row of its own, so ADR 0510 opens it as an uncertifiable `SC5001` (ADR 0509) instead of claiming the strict read. The rendered reads' `async-outside-loading-boundary` is a violation now that the mount resolves.
