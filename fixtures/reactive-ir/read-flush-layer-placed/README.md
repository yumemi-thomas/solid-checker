# read-flush-layer-placed

Claim (ADR 0859): a read in a layer that runs in place inside `flush(fn)` (an IIFE) is placed as a read directly in `fn`: where the `flush` call runs. Chrome (rc.21) is silent in `InJsxEach`, `InJsxCall`, `InJsxDirect` and `InMemo`. `InJsxEach` and `InJsxCall` were SC1001 false positives: uncertifiable now, as `InJsxDirect` always was, since the helper's run is not placed. `InMemo` has no row. `HelperInBody` warns in Chrome; a helper's call is not the proof that the IIFE runs in the body: uncertifiable, was a violation. `InBody` stays a violation. `RunAndKept`: the in-place run is tracked, the kept run is in the body, Chrome warns; the in-place run clears nothing: uncertifiable. Stubs: rc.21's `solid-js`, `@solidjs/signals` and `@solidjs/web` versions; `solid-js.d.ts` as strict as the published typings for what it calls.

Since the flip of ADR 0967's default (the review of #216) this fixture's program has an open boundary (no `.solid-checker/runtime.json`), so each `flush()` written in an exported function keeps an uncertifiable row of every code its program censuses ruled out (SC2006 `flush-in-action-unaccounted`, SC2008 `flush-in-effect-unaccounted`, SC3001 `leaf-operation-unaccounted`): an export may be entered by code this build cannot see, an action's step among it. The snapshot's additional rows are those; the claim above is unchanged.
