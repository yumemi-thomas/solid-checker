# flush-universe-package-hand-off-receivers

**Claim (the check of #227, G1, and its neighbours; ADR 0967 amended).** `this` and `super` name an object no reference of it shows. A member the receiver reaches (a getter, a method, an arrow, a function placed in the literal) runs where the receiver is read, so a flush it holds that an installed package the build does not read as source (`steplib`, as in `flush-universe-package-hand-off-causes`) may run as an action's step keeps its three uncertifiable rows (SC2006 `flush-in-action-unaccounted`, SC2008 `flush-in-effect-unaccounted`, SC3001 `leaf-operation-unaccounted`): never silence, never a violation. A value is placed in an object literal that writes a receiver when it is a property's value, a spread's argument or a `__proto__:` value; it is handed.

**G1.** The getter that flushes is on a prototype literal and a receiver in the derived object's accessor reads it in a step: `protoSuper` (`super.g`), `protoThis` (`this.g`), `protoWritten` (the prototype written after the literal: `o.__proto__ = base`), `protoDeep` (two levels up, the middle literal writes no receiver), `protoSetter`, `protoPicked` (the prototype named by a conditional) and `protoMethod` (a method on the prototype). Chrome (rc.21) reports FLUSH_IN_ACTION at each flush; before this, the checker certified them (`scripts/fuzz/patterns/pkghand/proto-*-step`).

**The neighbours, no prototype.** A method of the literal run through `this` in a closure a package runs (`ownMethod`; no call edge reaches it), the method handed through `this` (`ownValue`: `runStep(this.m)`), an arrow member read back by `const { m } = this` (`ownArrow`), a function written outside and placed in the literal (`placed`: `m: helper`), a prototype's members spread into the literal (`spread`) and a method written outside the literal that names `this` and is called on it (`foreign`, `foreignDerived`: the call binds the holder; `foreignImported` and `foreignShort` take it from another module, by a property and by a shorthand). `foreignParam`, `foreignCall`, `foreignAlias` and `foreignArray` are the same method reaching the literal in a way no reference resolves (the check of #229, B1): through a parameter, a call's result, an alias made by a destructuring, an array's element; a callee nothing resolves to one function is handed. `keyed` writes the prototype through a key the program does not name, in a program that spells `__proto__`.

**Twins, silent.** `twinNull`: a `null` prototype. `twinUnrelatedReader`: a receiver in a literal that is not the getter's. `twinOwn`: a literal whose method flushes and which writes no receiver. Each holder is a plain object literal bound by a `const` that no use makes a receiver (it is read, and its members are called by a callee that names no receiver), so a receiver of another object reading the same key (`g`, `m`) hands nothing stored in it. `renamedProto` and `renamedWritten` (the derived literal writes no receiver, so nothing reads the prototype's getter through one: the value goes on in the reads of the object, which are timers' callbacks), `renamedNull`, `renamedUnrelatedReader` and `renamedOwn` are the five shapes with a flushing member stored under a key of its own.

**The name net's known cost (the review of #229, B2).** `twinProto` and `twinWritten` were silent twins. Their getter is stored in a literal that is the prototype of another object (`{ __proto__: twinProtoBase }`, `twinWritten.__proto__ = twinWrittenBase`), which may be given a receiver, and the cases above read `g` through a receiver, so each keeps the three uncertifiable rows of its flush: a read of the same key on another object that a name cannot tell apart. Chrome (rc.21) is quiet at each; the answer is uncertifiable, never a violation.

Published bytes: `node_modules/steplib` is synthetic, as in the causes fixture; `@solidjs/web/types/index.d.ts` is the same excerpt. `.solid-checker/runtime.json` closes the program boundary.
