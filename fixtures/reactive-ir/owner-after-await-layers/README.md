# owner-after-await-layers

**Claim (ADR 0493).** An effect, cleanup, context read or boundary call in function layers that run in place (an IIFE, a project helper's callback, a function bound to a name and called once; ADR 0469's climb) runs on the stack of the outermost layer's call, so when that call follows an `await` on every path the operation runs on the await's continuation with no current owner, as one written directly after the `await` does. Violations: `IifeAfterAwait`, `HelperAfterAwait`, `ClosureAfterAwait`, `SettledCleanupAfterAwait` (an `onSettled` returning a cleanup, ADR 0488's operation). Silent: `IifeBeforeAwait`. Not violations (review): `GuardedAfterAwait` (a `getOwner()` guard in the function the climb ends in) and `ForEachAfterAwait` (a library callback may run zero times). Uncertifiable, unchanged: `ConditionalAwait` (the await is on one path). `DeferredAfterAwait` is silent, a known miss outside this claim: the helper hands its callback to `setTimeout` through a parameter, which the owner graph does not place.

Runtime: rc.17 warns `NO_OWNER_EFFECT` / `NO_OWNER_CLEANUP` for the layered forms (the misuse matrix, scripts/fuzz, Chrome-confirmed). Stub: `owner-after-await`'s.
