# handler-expression-setup

**Claim.** Only a function an event attribute's expression yields is the handler the compiler binds: the expression itself, a branch of a conditional, an element of an array, or the last operand of a sequence. Any other function in the expression runs, or not, while the expression evaluates at the element's setup, in the component body. So a read or a write in `onClick={((() => { … })(), handle)}`'s IIFE is the body's: `ReadInSetupIife` is `strict-read-untracked` and `WriteInSetupIife` is `no-write-in-pure-computation`, both violations. A read or a write in the handler itself stays legal: `ReadInSequenceHandler`, `WriteInSequenceHandler` (the sequence's last operand), `ReadInHandler`, `WriteInPickedHandler` (a branch).

Runtime: rc.17 evaluates the handler expression in the component's labelled untrack (`solid-js` dist/solid.dev.js:44-70), so a read there warns STRICT_READ_UNTRACKED and a write throws REACTIVE_WRITE_IN_OWNED_SCOPE; the fuzzer's `pos-handler-expr` cell (fast runtime, Chrome-sampled) reported 1,944 certified false cleans before this claim, when the expression's largest function was taken for the handler. Stub: `callee-callback-timing`'s.
