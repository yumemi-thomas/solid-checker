# flush-universe-package-hand-off-receiver-confinement

**Claim (the review of #232, B1, B2 and B5; ADR 0967 amended).** A function stored under a key that a receiver (`this`, `super`) reads, in code a package may run, is handed unless the holder provably cannot be a receiver (`holder_confined`: a plain `const` literal whose every use keeps it plain). That proof has premises, and each is checked here. (B1) What a use of the holder gives out is a name for an object of the holder's own, and its uses are asked in turn: a rest copy holds the same functions under the same keys, a nested literal bound by a pattern, read through a member or a chain, given to a function the build reads or copied by a spread is another name for the object that holds the function, and an exported holder is reached by the importers of a namespace picked by a key the analysis does not read (the namespace census). (B2) A key is the property key the runtime gives it, not its text: `\u006b` is `k`, and `0x1`, `1.0` and `1` are one property. (B5) A name an object pattern assignment rewrites (`({ s } = …)`) is no unique symbol. Each site keeps its three uncertifiable rows (SC2006 `flush-in-action-unaccounted`, SC2008 `flush-in-effect-unaccounted`, SC3001 `leaf-operation-unaccounted`): never silence, never a violation. Chrome (rc.21) reports FLUSH_IN_ACTION at each of these shapes written as a program of its own, and the head the review read certified each with no finding (`scripts/fuzz/patterns/pkghand/rest-copy-step`, `nested-*-step`, `key-*-step`, `symbol-rewrite-step`: one program each, judged by Chrome); in this combined program the rows are the checker's, a flush that does not run in Chrome (`keyFloat`: the getter's first read, `this[1]()`, throws before `this["2"]()`) keeps its rows as well, because the read of the key is in code a package runs.

**Why this program is not each case's proof.** The cases share one program, in which a spelled `__proto__` and a rewritten symbol hand some of the sites on the head the review read as well (a write through a key the program does not name where a file spells `__proto__` is a possible prototype install). The per-case proof that the review's head certified each is the pattern lane, one program per case.

**The cases.** `restCopy`, `nestedPattern`, `nestedRead`, `nestedChain`, `nestedArg` (the function that gives the prototype is a function the build reads), `restNested` (the getter runs `this.restNestedSub.restNestedM()`), `nestedSpread`, and `exported` (the flush is in `exported-holder.ts`; `import * as exported` is read with `(exported as any)[exportedName]`): the holder is given a prototype whose getter reads the key through `this` in a step the package runs. `keyEscapeStore`, `keyEscapeRead`, `keyEscapeMethod`, `keyProtoEscape` (`__\u0070roto__`), `keyHex`, `keyFloat`, `symbolRewrite`.

**Twins, silent.** Each reads a key a function stored in it is read under, and no use of the holder gives it a prototype, a receiver or a name nothing follows: `twinRestHolder` (a rest copy used as a value nothing takes), `twinNestedOuter` (a nested literal bound by a pattern, read through a member, a chain, copied by a spread), `twinLeafHolder` (a pattern parameter that names a key no object is held under), `twinKeyEscape` and `twinKeyNumber` (a key spelled with an escape, a number, that no receiver reads), `twinSymbol` (two distinct symbols: the read names the other one). The program also reads `Object.prototype.hasOwnProperty` and compares with `Object.prototype`: no accessor is installed, so every twin stays confined (`flush-universe-package-hand-off-object-prototype` is the program that gives it a member).

Published bytes: `node_modules/steplib` is synthetic, as in the reads fixture; `@solidjs/web/types/index.d.ts` is the same excerpt. `.solid-checker/runtime.json` closes the program boundary.
