# owner-call-inplace-nested

**Claim (batch 11, B2, the review of #225, the in-place rule; ADR 0971).** A dialect control-flow element (`For`, `Show`, `Index`, `Repeat`, `Switch`, `Match`, `Loading`, `Errored`) calls the function it is handed, and reads its getters, under the owner of its own render; a context provider reads its children there too. A JSX creation written **directly** in that function's body, or directly in the getter (no function between), runs there and throws nowhere: it is no site of the owner-call universe. A function written **inside** one of them is no part of that call. It runs where it is called, and if a stack with no owner calls it (here an effect's apply, through a variable) a tag is refused (rc.21 PRIMITIVE_IN_EFFECT_CALLBACK, SC6002): the tag in it is a site like any other. The in-place rule as first built dropped every site inside the handed function or the getter, nested functions included, and certified these programs (Chrome: oracle case `fixtures/runtime-oracle/owner-call-inplace-nested`, `unproven-clean` on that build, `covered-uncertifiable` now). A nested function keeps the usual analysis, which here ends in the code's own uncertifiable row (never a violation, never a silence).

| site | outcome | why |
|---|---|---|
| `<Inner />` written directly in `For`'s row function (line 16), in `Show`'s function child (19), in `Show`'s children (24), in a context provider's children (32) | silent | created in place, under the owner of the element's render |
| `view = () => <Inner />` written in `For`'s row function (line 43) and in `Show`'s function child (57), stored in `pickRow` / `pickShow` and called by `Host`'s apply | SC6002 `effect-creation-unaccounted` (uncertifiable) | a function written inside the handed function runs where it is called: here on the apply's stack with no owner. **The false clean this fixes** (Chrome: PRIMITIVE_IN_EFFECT_CALLBACK at the tag) |
| `pickIife = () => <Inner />` written in an immediately invoked arrow in `Show`'s children (line 71) | the same row | an arrow written inside an in-place getter runs where it is called, not where the getter is read |
| `pickMap = () => <Inner />` written in a `.map` callback in `Show`'s children (line 84) | the same row | the same |
| `pickProvider = () => <Inner />` written in an immediately invoked arrow in a context provider's children (line 97) | SC3001 `leaf-operation-unaccounted` and SC6002 `effect-creation-unaccounted` (uncertifiable) | the same, for a provider |
| `return () => <Inner />` in `makeView` (line 106), whose result `RowMade`'s row function keeps in `pickMade` | SC6002 at the closure, and the SC9012 `handed-member-read` at `pickMade!()` (line 129) | a closure made by a call to another function is written outside the element: the rule never sees it, and the usual analysis covered it on every build (Chrome: `owner-call-inplace-closure`, `covered-uncertifiable` before and after the fix) |

The Chrome oracle cases are `fixtures/runtime-oracle/owner-call-inplace-nested` (the five nested shapes, `ByRow`, `ByShow`, `ByShowIife`, `ByShowMap`, `ByProvider`, and an in-place control), `owner-call-inplace-closure` (the closures a called function makes), `owner-call-inplace-function` and `owner-call-inplace-function-ops` (the legal direct forms and the operations a handed function may hold: no row changes). The fuzz cells are `er-rownest-apply`, `er-shownest-apply`, `er-getteriife-apply`, `er-gettermap-apply` and `er-providernest-apply` and their never-run twins, with the JSX variants.

`node_modules/solid-js/index.d.ts` adds `For` (the first overload), `Show` (the non-keyed element-child and function-child overloads, joined) and `Context`/`createContext` to the usual reduction, from `solid-js@2.0.0-rc.21` `types/client/flow.d.ts:32, 101, 107` and `types/client/core.d.ts:13-16, 92`.
