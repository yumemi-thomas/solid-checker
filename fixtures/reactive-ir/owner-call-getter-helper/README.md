# owner-call-getter-helper

**Claim (batch 11, B2 of the re-review of #220; the review of #225, F2, found while fixing it; ADR 0971).** A **call** written in a component element's getter (a prop's value, the children) runs its callee where the component reads the prop, so it places no callee. `Outer` reads `props.slot` and `props.children` on an effect's apply, where no owner is set; `<Outer slot={renderView()} />` with `renderView` returning `<Inner />`, or calling `createMemo`, throws rc.21 PRIMITIVE_IN_EFFECT_CALLBACK at the tag and at the memo. The analyses that place a callee by the position of its call (the role engine, the owner graph's edge, the entry walk of `owner_emission::layer_entry_open`) took the call for a run in the render that wrote it, a component only a tag renders, and ended both sites silently on main, on #220's head and on the first build of B2 (and the first fix of F2, which made a creating call and a JSX written in a getter sites but left the callees of a call there alone). The entry walk now takes a layer a call in a getter enters for one entered by a run no edge shows (`written_in_getter`, in the local references, the other files' references and the callers it follows), so the callee's sites keep their rows (decline `entry-by-reference`, never a violation) unless something else proves them: the program census (`no-opener-in-program`) still ends a leaf code in a program that opens no leaf scope.

| site | outcome | why |
|---|---|---|
| `<Inner />` in `renderView`, called in `ByHelperSlot`'s prop (line 16; also the children, line 45, and `renderTwice`, a helper that calls it, line 51) | SC6002 `effect-creation-unaccounted` and SC3001 `leaf-operation-unaccounted` (uncertifiable) | the getter's call runs the callee where `Outer` reads the prop (Chrome rc.21: PRIMITIVE_IN_EFFECT_CALLBACK). **The false clean this fixes** |
| `createMemo` in `makeMemo` (line 20) and in the arrow `makeLocal` holds (line 28) | the same rows | a creating call in a function a getter calls |
| `<Tag />` in `sharedView` and `createMemo` in `sharedMemo`, imported from `helpers.tsx` and called in `ByImported`'s props (`helpers.tsx` lines 9 and 13) | the same rows | the other files' references are followed too: the caller is in a getter |
| `controlView`, `controlMemo` (called only in `Rendered`'s body) and `showMemo` (called in the getter of a `Show`, which renders it in place) | silent | a render enters them under the owner its render sets; an in-place renderer's getter is no getter |

The program is closed (`package.json`, private), so the exports of `helpers.tsx` are no hand-off of B3 (ADR 0967). The Chrome oracle case is `fixtures/runtime-oracle/owner-call-getter-helper` (every export is handed there, so B3 covers the sites on every build and the case records Chrome's truth only). The fuzz cells are `er-slothelper-apply` and `er-childhelper-apply` and their never-run twins, at module scope inside a module-level `createRoot` (B3 files no row there, so the helper's own proof decides): the false clean on #220's head and on the getter-only build, none with the entry walk's rule.
