# owner-call-generator-layer

**Claim (batch 11, slice 6; ADR 0969; the second re-review of #220, B1).** A generator's body runs where an iterator is stepped, not where the generator is called. The role engine places a generator's body by the call that makes the iterator (rendering, in a component's body), and the graph's contexts follow the same call edge, so the owner-call universe's silences speak for a site only where it is *plain*: not in a parameter list, not after a suspension, and not in a generator. The test asked the innermost function only, so a creation in a layer written *inside* a generator (an arrow its body calls, an IIFE, an `untrack` callback it runs in place) was a plain arrow and was ended by `EffectCreationRunsOffApply`, though an effect's apply that steps the iterator (`for...of`, a spread) runs the layer on its own stack with no owner (Chrome rc.21: PRIMITIVE_IN_EFFECT_CALLBACK). The question is now asked of every function layer around the site (`generator_layer_around`, `owners/leaf_universe.rs`), up to the layer whose callback runs under an owner its primitive creates (`creates_owner_for`: a root's or a memo's callback), which is current there whoever steps what is around it.

| site | outcome | why |
|---|---|---|
| `createMemo` in the arrow `run` that `StepForOf`'s generator calls, the apply steps it with a `for...of` | SC6002 `effect-creation-unaccounted`; decline `generator-body` | a generator layer around the site: its body runs where the iterator is stepped. **The false clean this fixes**: the head of #220 ended it with `effect-creation-runs-off-apply` |
| `createMemo` in the `untrack` callback `StepSpread`'s generator runs, the apply spreads it | the same | the same (an in-place primitive callback is a layer too) |
| `createMemo` in the IIFE `StepIife`'s generator runs | the same | the same |
| `createRoot` in `StepRoot`'s generator | SC6002 `effect-creation-unaccounted`; decline `generator-body` | the generator's own body (unchanged); it is what throws |
| `createMemo` in the callback of that `createRoot` | silent (`effect-creation-owner-set-around`) | **the owner layer stops the climb**: the root's owner is current in its callback however the generator is stepped (unchanged) |
| `createMemo` in `Idle`'s generator, which is made and never stepped | SC6002 `effect-creation-unaccounted`; decline `generator-body` | **the cost**: Chrome is quiet (the site never runs), but a generator layer is no plain site and nothing here proves the iterator is never stepped |

The Chrome oracle case (`fixtures/runtime-oracle/owner-call-generator-layer`) records the throw at the first three creations and at `createRoot` (the memo in its callback never runs; `Idle` is quiet) and every one is covered on the head and on the fix: the oracle's entry hands every export to `render` of the real `@solidjs/web`, a package nothing here reads, so B3 (ADR 0967) keeps a row at each creation on every build. The false clean is the closed run of this fixture (the components are rendered by tags from `App`, which `render` mounts): the head certifies the three creations (L13, L34, L52) and the build with the fix files a row at each. The fuzz cells `er-genlayer-apply` and `er-genuntrack-apply` (`scripts/fuzz/er-shapes.mjs`) hold the two shapes with a twin that never steps the iterator, the generator and its iterator at module scope (the grids' entry is the same hand-off to `render`, and B3 answers it with a row for everything written inside an exported component): the head certifies the three `genuntrack` programs (Chrome confirming), the fix none (rediscovery.json); the `genlayer` cells are covered by the ADR 0710 row at the creation on both builds.
