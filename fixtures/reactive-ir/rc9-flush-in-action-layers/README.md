# rc9-flush-in-action-layers

Claim (ADR 0478): `flush()` in function layers that run in place inside an action step (an IIFE, `[x].forEach`, a helper in this file or another module that calls its callback in its body, nested) throws `FLUSH_IN_ACTION` on rc.8+ dev (the `flush-in-action` page's probe table: a synchronous helper throws), so SC2006 is reported at it. Silent: a layer after the body's first await, a call after an async IIFE's own await, a scheduled callback, and a layer in the generator's parameter list. A helper that keeps its callback (`kept`) is uncertifiable since ADR 0832: no layer follows a closure handed to project code, and nothing proves the kept callback never runs on a step's stack (here nothing reads `saved`, which the checker does not prove). A named closure called once in place is claimed too (ADR 0479). Stubs as in `rc9-flush-in-action`. ADR 0516: a sync generator called in place whose iterator is used (`steppedGenerator`) and a named helper an action body calls that has other callers (`viaShared`) are uncertifiable; a generator whose iterator a statement discards (`discardedGenerator`) stays silent.

Since the flip of ADR 0967's default (the review of #216) this fixture's program has an open boundary (no `.solid-checker/runtime.json`), so each `flush()` written in an exported function keeps an uncertifiable row of every code its program censuses ruled out (SC2006 `flush-in-action-unaccounted`, SC2008 `flush-in-effect-unaccounted`, SC3001 `leaf-operation-unaccounted`): an export may be entered by code this build cannot see, an action's step among it. The snapshot's additional rows are those; the claim above is unchanged.
