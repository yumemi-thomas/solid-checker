# flush-universe-class

**Claim (batch 11, slice 5, the review of #213: B1 and B2).** The census class of the code around a flush (`FreshStack`, `AwaitContinuation`, `TestRunner`) says where the function around it runs, and ends all three codes only when it is a statement about the flush's own stack: the flush is written in the *body* of its function (a default value in a parameter list runs wherever the function is called, which the class of the code around it does not say: B2), and, for a scheduler's or a runner's callback, no function around it is a named function expression its own code uses (`setTimeout(function tick() { flush(); … tick(true) })` enters `tick` again on the stack of whatever calls the name, an action's step or an effect's apply: B1). Chrome (rc.21) reported FLUSH_IN_ACTION and FLUSH_IN_EFFECT_CALLBACK at those flushes while the checker certified them with a typed reason `FlushSafe::FreshStack` (and on main with no accounting at all); the fuzz cells `fc-*` (`scripts/fuzz/fc-shapes.mjs`) and `scripts/fuzz/patterns/flushclass` hold the shapes.

`App.tsx`: the program steps an action, runs an effect's apply and opens a leaf scope, so no program-wide reason holds. `Again`, `Each` (a carrier's named callback), `Default` (a default run in an apply) and `Awaited` (a default written after an `await`) each have an uncertifiable row of each code (twelve rows: `flush-in-action-unaccounted`, `flush-in-effect-unaccounted`, `leaf-operation-unaccounted`; at a default the SC2006 row is the producers' own `parameter-initializer-unplaced`, ADR 0961, so ten of the twelve are the accounting's), never a violation (nothing here proves the second run happens). Silent: `Once` (a named expression whose name nothing uses), `Direct` (the flush directly in the timer's callback) and `After` (past the await), each on a typed reason (`FreshStack`, `AwaitContinuation`). A reviewed test runner's callback has the same conditions: `flush-universe-test-runner`.

The re-review of #213 found three more shapes of the same cause, code written in the scheduler's callback that does not run when the callback runs, each certified with `FlushSafe::FreshStack` on the PR head (and with no accounting on main), each confirmed by Chrome in an effect's apply (the cells `fc-field-*`, `fc-gencarrier-*`, `fc-jsxprop-*`): `Field` (N1, a class field's initializer runs at construction: `Late = class { x = flush(); }`, `new Late()` in an apply), `Carrier` (N2, a generator handed to an inline carrier: `[1].map(function* () { flush(); })` only creates the generator object, `.next()` runs the body) and `Prop` (N3, a prop written in JSX is a getter that runs where the component reads `props.v`). Each has an uncertifiable row of each code the producers do not already row (at `Field` and `Carrier` the producers' own `function-run-unplaced` and `field-initializer-unplaced` rows stand for SC2006 and SC3001; at `Prop` the SC1001 row at the read stands, and the three flush rows are the accounting's). `Static` is silent in the accounting: a static initializer runs when the class is evaluated, which is when the timer's callback runs it.

The second re-review found one more shape of the same cause, in the call that hands the callback over rather than in the code written in it (N5, the cell `fc-recvthen-*` and the patterns `recvthen-*`, each confirmed by Chrome in an effect's apply, an action's step and a leaf callback): `catch` and `finally` run their handler through the receiver's `then` (ECMAScript 27.2.5.1), and a Promise subclass whose `then` runs the handler at once calls it on the stack of whatever called them. `Receiver` and `Finally` (a `Sync` receiver, in an effect's apply) have an uncertifiable row of each code (three rows each); `Plain` is refused as well (three rows: a plain `Promise` runs the handler later, but the inherited method resolves to the same standard declaration, so the proof refuses the call, as `runtime_semantics::dispatches_through_receiver_then` says for every consumer of `fresh_stack_callback_call`). A reviewed runner's suite body has the same questions asked of what is written inside the registration (N4): `flush-universe-inline-suite`.
