# context-package-no-default

**Claim (ADR 0943, ADR 0713).** A context a dependency creates with no default is not silent in the project that reads it. The package's own source says it has no default, and the providers of a package's context are not this program's to census (a router or a dialog may provide it itself), so a read under an owner with no provider proven above it is an SC4002 **obligation** (uncertifiable, `provider-not-proven-above`), never a violation and never silent. Before ADR 0943 `file_candidates` made every dependency `createContext` silent (`if dependency || proven.is_none()`), so the read below was certified clean while Chrome throws ContextNotFoundError (rc.21 `CONTEXT_NOT_FOUND`).

`App.tsx`, each component reads the package's `RouterContext` in its body:

- Obligation: `Bare` (no provider anywhere), `Alias` (the import renamed: the same binding), `Namespace` (`Router.RouterContext`: a member read names no binding the census can match), `Twice` (one render under `<RouterContext value>`, one outside: not every render is under a provider).
- Silent: `Provided` (every render of the reader sits under the provider, `provided_above`).

A context the syntax proves has a default stays silent as a named premise (`PremiseKind::ContextDefaultProven`, logged at the read): the project-context cases are `context-default-undefined`'s `DefaultReads`. A package hook that reads its own context inside the package's source is reported at the project call that runs it (ADR 0290): `context-read-package`'s `BodyHook` (kobalte's `useDialogContext`) is the same obligation there, and `HandlerHook`, which has no owner, stays SC4001's.

Source: `node_modules/dep-router-context/dist/index.js` lines 2 to 4 are `@solidjs/router` 2.0.0-next.26 `dist/index.js` lines 545 to 547, verbatim (file sha256 `b657bc8dde1275e710dccada942c4d0cd8c7d222e72a4dd0e298f9cce77baa35`; package `sha512-Zjho0HI095mxSMu8tyfuqoq8vTeYML0mWJj1iQar298MrhtT2itGiEgF2C7ndE2mzKeXRQ/DLf1tr37Gax5bsg==`, digest `e67af539…04d6`, as `route-config/variants/next26` records it), plus the import and the export `RouterContextObj as RouterContext`, which is one item of that file's line 3529 export list. The manifest is this fixture's own and has no `solid` condition (the published `index.jsx` re-exports from other files). `index.d.ts` abbreviates the published `Context<RouterContext>` (`dist/routing.d.ts` line 14) to `Context<object>`; no case reads a member. `tsc --noEmit` (TypeScript 5.9.3) is clean with the stub's `Context`, `createContext` and `useContext` (copied from the published rc.13 typings, as `context-provider-proof` does).

Runtime: `.solid-checker/runtime.json` selects `dep-router-context` as dependency source. Chrome (rc.21, development build) was measured through the fuzzer's `package` source (ADRs 0940, 0943; `fz-ctx` is the fuzzer's own package of the same shape): a program that reads the package's context directly, through an alias or through the namespace, with no provider above, throws ContextNotFoundError (210 generated programs: every context, binding and layer), and one that calls a package hook reading it does the same (42, the `direct` binding). This fixture's own `Provided` and `Twice` were not run in Chrome: `Provided` is silent because a provider is proven above its reader, and `Twice` is an obligation because one of its renders is not under one.

Not covered: a context a package creates behind a wrapper (the binding's initializer is not the call: not a candidate, as for a project's), a package context handed to code that provides it (the same obligation: the census no longer asks), and a provider the project renders above a package hook's call (not followed into the package: the call stays an obligation).
